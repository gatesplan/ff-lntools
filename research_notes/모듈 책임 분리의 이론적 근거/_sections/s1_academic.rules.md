# 2장(학술적 관점) 곁 파일: 규칙 후보와 ln-structure 시사점

출처 표기는 저자-연도이며, 서지는 `s1_academic.md` 의 "참고문헌 (2장)"에 있다. 본문에 없는 출처는 맨 끝 "본문 참고문헌에 없는 출처"에 적었다. "(노트의 추론)"은 노트 작성자가 발견 사항에서 끌어낸 추론이고 "(작성자 추론)"은 이 파일을 쓰며 덧붙인 추론으로, 둘 다 출처가 직접 말한 것이 아니다. 증거 강도는 종류(형식 논증 / 실증 / 전문가 의견)와 세기(강 / 중 / 약)로 적는다.

## 규칙 후보

1. **모듈은 처리 단계가 아니라 숨기는 설계 결정 하나(어렵거나 바뀔 만한 결정)를 기준으로 나눈다.**
   - 근거: KWIC 에서 처리 단계 분해는 저장 방식이 바뀌면 모든 모듈이 바뀌고, 정보 은닉 분해는 한 모듈만 바뀐다. 처리의 시간 순서는 분해 기준이 아니다. 환경 매개변수를 넣은 DSM 재분석도 정보 은닉 설계 쪽의 가치가 크다고 계산한다.
   - 출처: Parnas 1972; Parnas, Clements & Weiss 1985; Sullivan 외 2001
   - 강도: 형식 논증(사고 실험, 모형) + 전문가 의견, 중
   - 반론·한계: 측정이 없다. 바뀔 결정의 목록은 판단으로만 만들며 변경은 "often only predictable by specialists"다(Parnas 2009). 의존을 알기 전에 정한 경계는 가치 봉우리를 놓친다(Baldwin & Clark 2000 [2차 출처]; Sullivan 외 2001). 어떤 단일 분해도 모든 관심사를 담지 못한다(Tarr 외 1999).

2. **모듈 책임은 "무엇을 숨기는가", 곧 "X 가 바뀌면 바뀌어야 하는 곳"의 형태로 적고, 처리 단계("어떻게")로 적지 않는다.**
   - 근거: 모듈 안내서는 각 모듈의 비밀만 적는다. A-7E 항목은 "need to be changed if …" 형태의 변경 조건문이다. "how to …" 형태의 비밀은 처리 단계 분해를 이름만 바꾼 오용이다. 구조적 설계도 "what transformations occur …, not how the module is implemented"를 적으라 한다.
   - 출처: Parnas 2009; Bass 외 2003(PCW 내용은 [2차 출처]); Parnas 1994; Stevens 외 1974
   - 강도: 전문가 의견, 중
   - 반론·한계: 책임 문장의 품질을 검증한 연구가 없다. Stevens 는 "변환(기능)"을, Parnas 는 "비밀"을 적으라 하여 문장의 형식이 다르다. 주 비밀과 부 비밀의 구별(Bredereke 2002 [2차 출처])을 쓰면 한 줄에는 주 비밀만 적게 된다(작성자 추론).

3. **책임 문장을 1974년 문법 시험으로 점검한다: 복문·쉼표·동사 여럿(시험 1), 시간어(시험 2), 하나의 구체적 목적어가 없음(시험 3, "Edit All Data"), 생애 주기 단어(시험 4, initialize, clean-up)는 응집이 낮다는 신호다.**
   - 근거: 기능적 결속인 모듈은 단동사, 단일 구체 목적어, 비절차적 문장으로 묘사된다.
   - 출처: Stevens 외 1974
   - 강도: 전문가 의견(휴리스틱), 약. 평가자 간 신뢰도나 예측 타당도를 잰 연구가 없다.
   - 반론·한계: 시험은 코드가 아니라 문장의 문법을 읽는다. 단서("while still completely describing the module's function")가 하중을 지므로 문장이 내용을 다 담는지 대조해야 한다. 모든 판정에 "probably"가 붙는다. 기능의 수는 분해 수준에 따라 달라진다(Card 외 1986b). 초기화 모듈이 때로 가장 단순한 해법이라는 인정이 있다. 문구 판본도 다르다(1974년 안에서 문장과 구, Yourdon & Constantine 1979 재진술은 [미확인]).

4. **다른 모듈은 모듈 전체(공개 이름)로만 가리키고 내부 요소를 직접 참조하지 않는다. 클라이언트는 명세된 인터페이스에만 기댄다.**
   - 근거: 이름으로 모듈 전체를 가리키는 연결이 내부 요소를 가리키는 연결보다 결합이 낮다. 명세 밖 사실에 기대는 클라이언트는 "incorrect (even if it is working)"이다. 정보 은닉 정리: 인터페이스만으로 A 를 증명할 수 있으면 인터페이스를 지킨 B 의 변경은 A 를 바꾸지 않는다.
   - 출처: Stevens 외 1974; Parnas 2009; Liskov 2013; Bachmann 외 2000
   - 강도: 형식 논증 + 전문가 의견, 중
   - 반론·한계: 인터페이스는 시그니처가 아니라 가정의 집합이어서 구문 검사로는 순서, 단위, 형식 같은 의미 누출을 잡지 못한다(Parnas 2009). 정리의 전제(무엇을 숨길지 안다, 비밀을 드러내지 않고 인터페이스를 기술할 수 있다)는 실증되지 않았다.

5. **데이터 구조는 그 접근·수정 절차와 한 모듈에 두고, 형식·문자 코드·정렬 순서·처리 순서를 숨긴다.**
   - 근거: KWIC 의 다섯 규칙. 추상 자료형은 연산으로만 특징지어지고 표현은 클러스터 안에서만 보인다.
   - 출처: Parnas 1972; Liskov & Zilles 1974 [2차 출처]
   - 강도: 전문가 의견, 중
   - 반론·한계: Stevens 외 1974 와 Yourdon & Constantine 1979 의 척도에서 같은 데이터를 다루는 연산 묶음은 기능적보다 낮은 통신적 결속이고, 이를 높이 치는 것은 Myers 의 정보적 수준뿐이다(정의 원문 [미확인]). "X 를 소유한다"형 책임의 이론적 근거가 갈린다(노트의 추론).

6. **공유 전역 상태(공통 데이터 영역)를 모듈 사이 연결 수단으로 쓰지 않는다.**
   - 근거: 원소 N 개를 모듈 M 개가 공유하면 전파 경로가 N·M·(M−1)개다.
   - 출처: Stevens 외 1974
   - 강도: 형식 논증(경로 계산), 중. 실증은 약하다.
   - 반론·한계: NASA 자료에서 COMMON 결합과 매개변수 결합 사이에 결함률 차이가 없었다(Card 외 1986a).

7. **사용(uses) 관계에 순환을 두지 않는다. 그러면 층을 계산할 수 있다: 0층은 아무것도 쓰지 않는 것, i층은 i−1층의 것을 하나 이상 쓰고 그보다 높은 층은 쓰지 않는 것.**
   - 근거: 층마다 시험하고 쓸 수 있는 부분 집합이 생기고 "nothing works until everything works"를 막는다. 어떤 유효한 층 체계도 상위 층의 무제한 사용을 허용하지 않는다.
   - 출처: Parnas 1978; Dijkstra 1968; Bachmann 외 2000
   - 강도: 형식 논증(정의), 강. 실증은 혼재해 중: 모듈을 가로지르는 순환은 강한 결함 패턴(Mo 외 2015), 큰 순환을 품은 핵심부 파일은 결함 3.4배(Sturtevant 2013), Clio 의 확인 위반에서 순환이 JDT 최다(Wong 외 2011)였으나, 패키지 순환은 여섯 반패턴 중 영향이 가장 작았다(Mo 외 2021).
   - 반론·한계: uses 는 정확성 의존이지 호출이나 import 가 아니다(Parnas 1978). 비순환은 간선 방향의 옳음을 보장하지 않는다. "not all cyclical relations are harmful"이고(Xiao 외 2014), 방문자 패턴은 본래 순환이다(Mo 외 2021).

8. **의존 간선의 방향은 Parnas 의 네 기준으로 정한다: A 가 B 덕에 본질적으로 단순해지는가, B 가 A 를 못 써도 크게 복잡해지지 않는가, B 를 포함하고 A 는 필요 없는 유용한 부분 집합이 있는가, A 를 포함하되 B 는 없는 유용한 부분 집합은 없는가.**
   - 출처: Parnas 1978
   - 강도: 전문가 의견, 중. 검증 연구는 없다.
   - 반론·한계: 기계로 계산할 수 없다. TSE 1979 판의 셋째 조건 문구는 [미확인]이다. 같은 논문은 "some duplication of effort seems preferable to a system in which nothing runs unless everything runs"라고도 한다.

9. **모듈과 층을 같은 것으로 다루지 않는다. 한 비밀을 공유하는 코드는 여러 층에 걸칠 수 있다.**
   - 근거: 샌드위치 분할 대부분이 "층 = 모듈" 가정에서 나왔다. 메모리 관리자의 두 조각은 두 층에 걸치지만 한 비밀을 공유한다. A-7E 에서 층은 모듈의 일부에 대응했다. PCW 의 비밀 트리는 누가 누구를 부를 수 있는지와 별개다.
   - 출처: Parnas 1978; Habermann, Flon & Cooprider 1976; Bachmann 외 2000; Bass 외 2003
   - 강도: 형식 논증 + 경험 보고, 중
   - 반론·한계: 모듈이 여러 층에 걸치는 설계를 실증으로 시험한 연구는 없다(Habermann 외 1976 이후).

10. **층에 "추상 수준" 같은 의미를 붙이지 않는다. 층은 정의된 비순환 관계에서 계산된 순위로만 말한다.**
    - 근거: "levels of abstraction"은 대개 "an abuse of language"이고, "more abstract than" 관계는 정의되지 않았다. 층은 하위 층으로 구현되는 함수 이름의 집합이며 컴파일 시점에 검사할 수 있다.
    - 출처: Parnas 1978; Parnas 2009; Habermann, Flon & Cooprider 1976
    - 강도: 형식 논증 + 전문가 의견, 중
    - 반론·한계: 의미 진영은 층을 응집된 가상 기계로 정의하고 "Layers cannot be derived by examining source code"라 한다(Bachmann 외 2000; Garlan & Shaw 1993; Buschmann 외 1996). SEI 전술은 "Maintain Semantic Coherence"를 든다(Bachmann, Bass & Nord 2007). 두 진영을 통제 비교한 연구는 없다.

11. **하위가 상위를 불러야 하면 '사용'이 되지 않게 한다: 상위 처리기를 데이터(콜백)로 넘겨받고 상위 이름을 하위에 박아 넣지 않는다. 구성 요소는 몇이 자신을 쓰는지 알지 않는다.**
    - 근거: 콜백은 "upward invocation, but not uses"이며, 처리기 이름이 하드코딩되지 않는 한 하위 층의 이식성이 유지된다. "there is never any reason for a component to 'know' how many other programs use it".
    - 출처: Bachmann 외 2000; Parnas 1978
    - 강도: 전문가 의견, 중
    - 반론·한계: 콜백·이벤트 결합은 구문상 보이지 않아 정적 분석이 놓친다(Cataldo 외 2009). 보이지 않게 엮인 효과는 지역 추론을 해친다(Constantinides 외 2004).

12. **조합(구현 선택, 연결, 설정)은 조각들보다 한 단계 위, 애플리케이션 진입점에서 한다. 라이브러리 코드는 기본 동작이 없는 얇은 API 에만 의존한다.**
    - 출처: Tarr 외 1999; Seemann 2011; Python Logging HOWTO; Rust log 0.4.34; OpenTelemetry 문서; Go context 문서
    - 강도: 형식 논증(Tarr) + 전문가 의견, 중
    - 반론·한계: 호출 지점은 여전히 흩어진다. 명시적 맥락 전달 자체가 산재이며, Rhino 에서 가장 흩어지고 결함이 많았던 관심사가 바로 메서드마다 범위 매개변수를 넘기는 방식이었다(Eaddy 외 2008).

13. **공개 인터페이스(설계 규칙)는 환경 변화에 불변이게 정하고, 서로 다른 외부 힘(운영체제, 데이터 규모, 사용자 등)이 움직이는 것은 다른 모듈로 나눈다.**
    - 근거: 정보 은닉은 환경 매개변수와 설계 규칙이 만나는 칸이 비어 있는 상태다. Line Store 와 Input 은 움직이는 힘이 달라 나뉜다.
    - 출처: Sullivan 외 2001
    - 강도: 형식 논증(모형, 예시 하나), 약~중
    - 반론·한계: 순옵션가치 수치는 대략적 추정이며 저자들이 실무 사용을 권하지 않는다. 환경 매개변수 목록도 판단이다.

14. **공통 부분을 새 모듈로 떼어 낼 때는 그것이 새 설계 규칙이 되어 구조를 경직시킨다는 비용을 감안한다. 이름 없는 잡동사니 모듈(util, common)은 만들지 않고, 공통 이름 요소로 나눈다.**
    - 근거: Baldwin & Clark 의 역전(inversion)은 더 실험할 이득이 비용을 넘지 못할 때 쓰며, 층이 늘수록 구조가 경직된다. util·common 은 무엇을 담는지 알려 주지 않고 의존을 끌어모은다.
    - 출처: Baldwin & Clark 2000 [2차 출처]; Gamba & Fusari 2009; Ajmani 2015
    - 강도: 형식 모형(2차) + 전문가 의견, 약
    - 반론·한계: Parnas 1978 은 두 프로그램의 비슷한 기능을 "a fundamental error in my thinking"의 신호로 보면서도 약간의 중복이 전부 아니면 전무인 시스템보다 낫다고 한다. 실무에서 공유 인프라를 한곳에 모을지(Microsoft 2009) 실패 단위 가까이 둘지(Jewson 2023)도 갈린다.

15. **많이 기대어지는 모듈(팬인이 큰 모듈)은 사실상의 설계 규칙이므로, 그 공개 표면의 변경을 가장 엄격하게 다룬다.**
    - 근거: 순옵션가치 모형은 설계 규칙의 비용을 그것에 직접 의존하는 모듈들에 걸친 가시성 비용(Z)으로 둔다. Cai 그룹은 옵션 가치가 큰 모듈을 "small …, with high technical potential …, and with few dependents"로 읽는다. 영향력 큰 파일이 자주 함께 바뀌는 불안정 인터페이스가 가장 강한 결함 패턴이었다.
    - 출처: Sullivan 외 2001; Mo 외 2016; Mo 외 2015; Mo 외 2021; Sturtevant 2013
    - 강도: 실증(상관, 주로 한 연구 그룹), 중
    - 반론·한계: 불안정 인터페이스 탐지는 변경 이력이 필요하고 임계값이 수작업이며 독립 재현이 없다.

16. **같은 층의 모듈은 서로 의존하지 않게 한다(서로 독립).**
    - 근거: 설계 규칙 위계의 정의적 성질이다. Apache Ant 에서 같은 층 모듈의 개발자들은 층을 가로지를 때보다 소통이 적었다. DL 은 이런 독립 모듈이 많을수록 높고 유지보수 대리 지표와 상관한다.
    - 출처: Xiao 외 2014; Wong 외 2009; Mo 외 2016
    - 강도: 실증, 약~중(한 프로젝트의 소통 자료, 한 그룹의 상관 연구)
    - 반론·한계: V&B 는 같은 층 사용을 대개 허용한다(Bachmann 외 2000). 의존에서 층을 만들면 층이 늘어난다("We start with a few levels and end up with many", Parnas 1978; "proliferation of levels", Habermann 외 1976).

17. **함께 바뀌는 것은 한 모듈에 둔다. 모듈 경계를 넘는 반복 공변경은 경계 오류나 숨은 결합의 신호로 검토한다(차단보다 리뷰).**
    - 근거: 모듈 경계를 넘는 공변경이 모듈 안 공변경보다 결함과 더 상관했다. 논리 의존이 구문 의존보다 결함 분산을 훨씬 많이 설명했다. Clio 의 모듈성 위반은 40~66%가 나중에 개발자에게 확인되었다.
    - 출처: Kouroshfar 외 2015; Cataldo 외 2009; Wong 외 2011; Zimmermann 외 2003; Martin & Martin 2007 [2차 출처]
    - 강도: 실증(상관), 중
    - 반론·한계: 약 48%의 공변경 클러스터는 문어형이고 개발자는 이를 캡슐화하기 어려운 정상 분포로 본다(Silva 외 2019; Silva 외 2015 [2차 출처]). 커밋 정책, 잡음, 파일 단위 측정이 결과를 흔들고 이력은 새 코드를 예측하지 못한다(Zimmermann 외 2003, 2005). 거친 최상위 패키지를 모듈로 삼으면 효과가 뒤집혔다(Kouroshfar 외 2015). Clio 정밀도는 하한 추정이며 두 시스템뿐이다.

18. **정적 import 도달 범위를 변경 예측으로 쓰지 않는다. 인터페이스가 바뀔 때의 최악 범위로만 읽는다.**
    - 근거: 직접 구문 의존의 74.3%와 97.3%는 함께 바뀐 적이 없다(과대). 명시적 의존이 없거나 반대 방향으로만 있는 이름 없는 결합이 Hadoop 확인 위반의 66/152 였고, 문서·설정·다른 언어 구현과의 결합은 정적 분석에 보이지 않는다(과소). 클라이언트의 변경이 의존 방향을 거슬러 의존 대상을 바꿨다(방향). 전파 비용은 모든 전이 경로를 같은 비용으로 센다.
    - 출처: Cataldo 외 2009; Wong 외 2011; Zimmermann 외 2003; Zimmermann 외 2005; MacCormack 외 2006
    - 강도: 실증, 중
    - 반론·한계: 자료가 C/C++ 와 Java 다. 전이 폐포(영향 범위)와 관측 공변경을 직접 비교한 연구는 노트에 없다.

19. **구조 응집 지표로 '책임 하나'를 판정하지 않는다. 구조 신호(모듈 안 연결 요소 수 등)는 분할 후보를 제시하는 데 그치고, 판정은 책임 문장과 어휘, 사람의 판단에 맡긴다.**
    - 근거: LCOM 은 결함 예측에서 무의미하거나 성적이 나빴고, 응집 지표끼리 55%의 경우에 어긋났으며, 구조 결합은 개발자 판단과 가장 불일치했다. 개발자는 "very similar responsibilities"를 기준으로 결합을 판단했고, 어휘 기반 지표가 개발자 판단에 더 가까웠다. 연결 요소 k>1 은 k 개로 나눌 가능성을 시사한다.
    - 출처: Basili 외 1996; Radjenović 외 2013; Ó Cinnéide 외 2017; Bavota 외 2013; Marcus 외 2008; Hitz & Montazeri 1995; Counsell 외 2006
    - 강도: 실증, 중(구조 응집 지표가 약하다는 결과가 반복된다)
    - 반론·한계: 어휘 기반 지표도 선언된 목적과 비교해 검증된 적은 없다. 결합 지표 결과는 클래스 크기에 일부 교란된다(El Emam 외 2001; 반론 Evanco 2003).

20. **모듈은 비밀이 독립적으로 바뀔 수 있을 때만 나누고, 쉽게 교체될 만하면 나누기를 멈춘다. 지나친 분리는 모자란 분리만큼 나쁘다.**
    - 근거: PCW 의 분할 규칙(새 비밀을 만들지 않고 옛 비밀을 세분, 공유 비밀 없음). 구조적 설계의 멈춤 기준(따로 쓸모 있는 원소 부분 집합이 없고 구현 전체를 한 번에 파악할 수 있음).
    - 출처: Parnas 2009; Tarr 외 1999; Stevens 외 1974; Candela 외 2016
    - 강도: 전문가 의견, 중
    - 반론·한계: 멈춤 기준이 출처마다 다르다(교체 용이성, 쓸모 있는 부분 집합, 파악 가능한 크기). DL 은 작은 독립 모듈이 많을수록 높지만 5파일 기준은 약한 휴리스틱이다(Mo 외 2016).

21. **어느 축의 변화를 국소화할지(새 변형 추가 대 새 연산 추가) 정하고 그 축으로 모듈을 나눈다. 다른 축의 변경은 여러 모듈을 건드린다는 점을 받아들인다.**
    - 근거: 객체(변형 기준)와 추상 자료형(연산 기준)은 한쪽의 강점이 다른 쪽의 약점인 쌍대다.
    - 출처: Wadler 1998; Cook 2009; Tarr 외 1999
    - 강도: 형식 논증, 강(쌍대성 자체)
    - 반론·한계: 언어 수단이 이 교환을 완화하지만 독립 확장의 통합은 2009년까지 완전히 풀리지 않았다(Cook 2009).

22. **아키텍처 규칙을 명시하고 기계로 지속 검사해 침식(위반)을 막되, 표류와 숨은 결합은 별도 수단(이력, 리뷰)으로 본다.**
    - 출처: Perry & Wolf 1992; Li 외 2022; Li 외 2021; Sangal 외 2005
    - 강도: 전문가 의견 + 문헌 지도, 약~중
    - 반론·한계: 대책을 검증한 연구가 드물고, 설계 결함은 정적 분석으로 자주 발견되지 않는다(Li 외 2021). DSM 규칙 검사의 효과도 평가되지 않았다(Sangal 외 2005).

23. **인터페이스(다른 모듈이 기대도 되는 가정)를 문서로 적는다.**
    - 근거: "Information Hiding was the second of two papers. The first was on interface specification. The second without the first would be a disaster." 명세는 사용자와 제작자 사이의 인터페이스다. 문서는 주석에서 뽑아낸 것이 아니다.
    - 출처: Parnas 2009; Dijkstra 1974
    - 강도: 전문가 의견, 중
    - 반론·한계: 인터페이스 문서의 형식이나 효과를 시험한 연구는 노트에 없다.

## ln-structure 시사점

### 뒷받침

- **모듈마다 책임 한 줄, "무엇"만 적고 "어떻게"는 적지 않는다.** 모듈 안내서는 비밀만 적고(Parnas 2009), "how to …" 비밀은 오용이며(Parnas 1994), 구조적 설계도 "not how the module is implemented"를 요구한다(Stevens 외 1974).
- **사람이 책임을 정하고 에이전트가 구현한다.** 모듈은 서브프로그램이 아니라 책임 할당이자 작업 배정이고(Parnas 1972), 성질을 진술하는 일과 그 성질을 보장하는 물건을 만드는 일은 나뉘며 명세가 둘 사이의 인터페이스다(Dijkstra 1974). Parnas 1971 은 설계자가 구현자에게 가는 정보를 통제해야 한다고 했다: "We should not expect a programmer to decide not to use a piece of information" [2차 출처: Colyer 블로그, 노트의 관련성 절에만 있음]. 모든 파일을 읽을 수 있는 에이전트에게 표면이 이 통제를 대신한다(노트의 추론).
- **표면으로만 import 한다.** 이름으로 모듈 전체를 향하는 연결이 결합이 낮고(Stevens 외 1974), 사용하는 모듈은 명세에만 의존하며(Liskov 2013), 명세 밖 사실에 기대면 틀린 것이다(Parnas 2009). 설계 규칙에만 의존하는 모듈이 숨은 모듈이다(Sullivan 외 2001).
- **중첩 모듈은 맨 위 안쪽 층만 공개한다.** 안쪽 층은 인접한 바깥 층 외에는 숨기고 고른 기능만 내보내는 층 구조(Garlan & Shaw 1993), 아래 층 함수의 가시성을 위 층이 재량으로 정하는 구조(Habermann 외 1976), PCW 의 숨은(H) 하위 모듈과 지역 안내서(Bredereke 2002 [2차 출처]), 줄 저장 모듈 안에서 "completely invisible to the rest of the system"이었던 기호표(Parnas 1972)와 닮았다.
- **층은 의존으로 계산되고 의미가 없다.** "모듈의 층 = 의존하는 모듈의 최고 층 + 1, 의존이 없으면 0"은 Parnas 의 층 정의와 같다(Parnas 1978). "levels of abstraction"은 대개 말의 남용이고(Parnas 1978), 루프 없는 관계를 정의해야 "levels"를 말할 수 있으며(Parnas 2009), 층은 함수 이름의 집합으로 컴파일 시점에 검사된다(Habermann 외 1976).
- **더 낮은 층이면 어느 층이든 import 할 수 있다.** Parnas 의 정의 자체가 i층이 i−1층 이하를 쓰는 느슨한 위계이고(Parnas 1978), V&B 도 아래 어느 층이든 쓰는 체계를 인정한다(Bachmann 외 2000).
- **모듈 사이 순환을 금지한다.** 순환이 없어야 층마다 시험하고 쓸 수 있는 부분 집합이 생긴다(Parnas 1978; Dijkstra 1968). 모듈을 가로지르는 순환은 강한 결함 패턴이었고(Mo 외 2015), 큰 순환을 품은 핵심부 파일은 결함이 3.4배였으며(Sturtevant 2013), Clio 의 확인된 위반에서 순환 의존이 JDT 최다(72/161), Hadoop 둘째(58/152)였다(Wong 외 2011).
- **모듈 안 파일 사이 순환은 허용한다.** "not all cyclical relations are harmful"이고(Xiao 외 2014), 해로운 순환은 모듈을 가로지르는 쪽이며(Mo 외 2015), 모듈은 함께 설계되고 함께 바뀌는 프로그램 전부를 포함한다(Parnas 1978).
- **같은 층 import 를 금지한다.** 같은 층 모듈이 서로 독립인 것은 설계 규칙 위계의 정의적 성질이고(Xiao 외 2014), 같은 층 모듈의 개발자는 소통이 적었다(Wong 외 2009). 모듈을 병렬 에이전트에게 나눠 맡길 때 관련된다(노트의 추론).
- **import 부수효과로 스스로 등록하지 않고 진입점에서만 연결한다.** 구성 요소는 몇이 자신을 쓰는지 알 필요가 없고(Parnas 1978), 상위 처리기 이름을 하위에 하드코딩하지 않는다(Bachmann 외 2000). 발행-구독·이벤트 결합은 구문상 보이지 않으므로(Cataldo 외 2009) 명시 연결이 그것을 정적 도구가 보는 곳으로 끌어낸다(노트의 추론). 보이지 않게 엮인 효과는 추론을 해친다는 AOP 비판(Constantinides 외 2004), 조합 규칙은 한 단계 위에 둔다는 제안(Tarr 외 1999), 구성 루트와 "라이브러리는 퍼사드, 애플리케이션은 설정" 지침(Seemann 2011; Python Logging HOWTO; Rust log 0.4.34; OpenTelemetry 문서)과 맞는다.
- **의존성 역전(추상화 도입)은 필요한 곳에만 둔다.** 분할로 도입한 추상 자료형 인터페이스는 설계 규칙이 되고, 옵션 가치는 기술적 잠재력, 곧 현실적 대안이 있을 때만 생긴다(Sullivan 외 2001의 순옵션가치 모형에서의 추론).
- **공통 부분을 떼어 이름 있는 모듈로 만든다.** 잡동사니 패키지를 피하고 공통 이름 요소로 나누라는 지침(Ajmani 2015)과 맞고, 책임 한 줄 규칙은 util·common 을 구조적으로 배제한다(노트의 추론). 공유 코드를 아래로 내리는 것은 Baldwin & Clark 의 역전을 뒤집은 그림이다(노트의 추론).
- **모듈은 타입만 공개하고, Rust impl 은 그 타입이나 트레이트의 모듈 안에만 둔다.** 데이터 구조와 접근 절차를 한 모듈에 두는 규칙(Parnas 1972), 연산으로만 특징지어지는 추상 자료형과 클러스터(Liskov & Zilles 1974 [2차 출처])와 맞는다. 표현 문제의 행렬에서 각 칸(impl)을 행(타입) 쪽이나 열(트레이트) 쪽에 고를 수 있으면 두 축의 확장이 모두 국소적으로 남는다(Cook 2009 에서의 노트의 추론). Cai 그룹도 설계 규칙을 인터페이스와 추상 클래스, 곧 타입으로 본다(Xiao 외 2014; Mo 외 2016).
- **편집마다 규칙을 검사한다.** 하중을 받는 제약을 장식과 구분하고 의존·일관성 분석을 하라는 처방(Perry & Wolf 1992), 침식 탐지 연구의 약 56%가 적합성 검사를 쓰고 "아키텍처 도구 부족"이 침식 원인 목록에 있다는 지도(Li 외 2022), 위반 검사를 회귀 시험처럼 돌리고 정당한 위반이면 규칙을 고쳐 진화를 명시하라는 제안(Sangal 외 2005)과 맞는다.
- **책임 한 줄과 도구가 만드는 문서.** 지식 증발과 이해 부족은 비기술적 침식 원인으로 꼽히고(Li 외 2022), 모듈 안내서는 "the only document read by all"이다(Parnas 2009). 세션 사이 기억이 없는 에이전트는 사실상 개발자가 계속 바뀌는 셈이라 이 대책의 가치가 더 크다(노트의 추론).
- **작은 폴더 모듈과 파일당 클래스 하나는 공변경 분석의 단위 문제를 피한다.** 파일 단위 공변경은 오도할 수 있고(Zimmermann 외 2003), 거친 최상위 패키지를 모듈로 삼으면 효과가 뒤집혔다(Kouroshfar 외 2015). 파일당 클래스 하나면 파일 단위가 클래스 단위와 같아진다(노트의 추론).
- **`lnt review` 의 "숨은 타입 노출" 질문.** 인터페이스는 내부를 가능한 한 적게 드러내야 하고(Parnas 1972), 정보 은닉 정리는 비밀을 드러내지 않고 인터페이스를 기술할 수 있다는 전제에 기댄다(Parnas 2009).

### 도전하거나 어긋나는 것

- **모듈은 폴더나 클래스가 아니라 결정(비밀)이다.** 구조만 보는 DSM 은 Parnas 의 처리 단계 분해도 모듈적이라 평가했고(Sullivan 외 2001), Parnas 는 사람들이 문법과 유행어에 매달려 설계 원칙을 잊는다고 했다(Parnas 2009). `lnt check` 통과가 정보 은닉을 보여 주지 않는다(노트의 추론).
- **인터페이스는 시그니처가 아니라 가정이다.** 표면은 이름과 타입만 검사하므로 순서, 단위, 시점, 공개 속성의 형식 같은 의미 누출은 통과한다(Parnas 2009 에서의 노트의 추론). KWIC 의 순환 이동 순서처럼 과잉 명세된 인터페이스도 구문 검사는 통과한다(Parnas 1972).
- **"무엇을 맡는지" 줄은 단계형 비밀을 허용한다.** "입력 파싱을 맡는다" 같은 줄은 Parnas 가 말한 "how to …" 오용이다(Parnas 1994). Parnas 의 시험은 어떤 결정이 숨겨지고 어떤 변경이 안에 머무는지다.
- **"X 를 소유한다"형 책임의 이론 근거가 갈린다.** 구조적 설계 척도에서 같은 데이터를 다루는 연산 묶음은 기능적보다 낮은 통신적 결속이고, Myers 의 정보적 수준만 이를 높이 친다(Stevens 외 1974; Yourdon & Constantine 1979 [2차 출처]; Myers 1978 [2차 출처]). 정보 은닉(Parnas 1972)은 데이터와 접근 절차의 동거를 지지한다. ln-structure 는 어느 이론에 기대는지 밝혀야 한다.
- **"책임 정확히 하나"와 "비밀 하나"는 다르다.** PCW 는 함께 바뀌는 비밀들을 한 모듈에 두고 독립적으로 바뀔 때만 나누며, 지나친 분할은 흩어진 비밀을 낳는다(Parnas 2009). 지나친 분리는 모자란 분리만큼 나쁘고(Tarr 외 1999), 응집·결합 최적화가 개발자의 목표라는 실증도 없다(Candela 외 2016). 모듈마다 표면 파일이 생기는 매우 잘게 나뉜 구조에는 인터페이스 비용이 붙는다(노트의 추론).
- **분해와 층이 한 구조로 묶여 있다.** PCW 의 비밀 트리는 uses 위계와 별개이고 어느 모듈의 접근 프로그램이든 트리 위치와 무관하게 쓸 수 있다(Bass 외 2003; Bredereke 2002 [2차 출처]). 한 비밀을 공유하는 모듈이 여러 층에 걸칠 수 있고(Habermann 외 1976), 샌드위치 분할 대부분이 "층 = 모듈" 가정에서 나왔다(Parnas 1978). 모듈마다 층이 하나인 ln-structure 에서는 그런 비밀을 두 모듈로 갈라야 한다. 중첩 모듈도 형제 모듈이 안쪽 두 층 사이에 끼어들 수 없어 이를 풀지 못한다(노트의 추론).
- **층은 설계 결정이지 코드 사실이 아니라는 입장이 있다.** "Layers cannot be derived by examining source code"이고 층 관계는 실제 사용이 아니라 허용 사용이다(Bachmann 외 2000). 계산된 층은 uses 뷰일 뿐이어서, 에이전트가 import 를 더해 모듈의 층이 조용히 올라가도 비교할 의도 층이 없다(노트의 추론).
- **import 는 uses 가 아니다.** uses 는 정확성 의존이라, 조건부로 부르기만 하는 호출은 사용이 아니고 인터럽트처럼 부르지 않는 사용도 있다(Parnas 1978). import 는 타입 전용 참조로 uses 를 과대 근사하고 공유 상태, 연결된 콜백, 프레임워크 관례를 놓쳐 과소 근사한다(노트의 추론).
- **비순환만 보고 방향은 보지 않는다.** 간선 방향은 Parnas 의 네 기준이 정하는데, 비순환 그래프도 방향이 틀릴 수 있다(스케줄러가 파일 시스템을 쓰는 예, Parnas 1978).
- **같은 층 사용 금지는 표준이 아니다.** V&B 는 같은 층 사용을 대개 허용하는데 그것이 층이 주는 수정 용이성을 해치지 않기 때문이다(Bachmann 외 2000). 의존에서 층을 만들면 층이 늘고(Parnas 1978; Habermann 외 1976), 금지하면 위계가 더 깊어진다(노트의 추론).
- **의미 진영은 층을 응집과 묶는다.** POSA·Garlan & Shaw·V&B 와 SEI 의 "Maintain Semantic Coherence"는 층을 응집된 서비스로 정의하고(Buschmann 외 1996; Garlan & Shaw 1993; Bachmann 외 2000; Bachmann, Bass & Nord 2007), Fowler 는 큰 시스템의 최상위 모듈이 도메인을 따라야 하며 세 층 구조는 작은 단위에서만 쓰라고 한다(Fowler 2015).
- **엄격한 관례의 지표에서 층 건너뛰기 import 는 위반으로 잡힌다.** 층 건너뛰기(skip-call) 지표가 있고(Sarkar 외 2009 [2차 출처]), 열린 층 관례에서는 이를 허용한다(Thakare & Kiwelekar 2021). 느슨한 층은 결합을 늘린다(Bachmann, Bass & Nord 2007).
- **층 위치에는 의미가 있다.** 많이 기대어지는 낮은 층 모듈은 사실상 설계 규칙이고 그 안정성이 가장 중요하다. 가장 강한 결함 패턴인 불안정 인터페이스는 import 규칙으로 막히지 않는다(Mo 외 2015; Mo 외 2021; Sturtevant 2013).
- **가장 엄하게 금지하는 것의 실증 효과가 가장 작을 수 있다.** 패키지 순환은 여섯 반패턴 중 영향이 가장 작았다(Mo 외 2021). 다만 모듈을 가로지르는 순환(Mo 외 2015)과 Clio 의 순환 증상(Wong 외 2011)은 반대 방향의 증거여서 결과는 혼재다.
- **비순환 층만으로는 부족하다.** 높은 팬인·팬아웃과 공변경을 함께 가진 허브(Crossing), 숨은 공변경, 불안정 인터페이스는 순환을 요건으로 하지 않으므로 비순환 시스템에서도 생긴다(Mo 외 2021; Wong 외 2011 에서의 노트의 추론).
- **`lnt blast` 는 영향 범위가 아니라 정적 도달 범위다.** 과대: 직접 구문 의존의 74~97%는 함께 바뀌지 않았고, 메모리 관리나 출력 같은 기본 라이브러리는 결합이 높아도 "very stable and unlikely to fail"이다(Cataldo 외 2009). 과소: 명시적 의존이 없거나 반대 방향으로만 있는 결합이 Hadoop 확인 위반의 66/152 였고 문서·설정·다른 언어 결합은 보이지 않는다(Wong 외 2011; Zimmermann 외 2005). 방향: 클라이언트 변경이 의존 대상으로 내려가는 경우를 상위 importer 목록은 표현하지 못한다(Wong 외 2011). 전파 비용 같은 전이 폐포 지표는 모든 경로를 같은 비용으로 세어 다시 내보내는 표면(퍼사드)을 인정하지 않는다(MacCormack 외 2006 정의에서의 추론).
- **import 만 보는 검사기는 가장 강한 침식 신호를 못 본다.** 이력에 기반한 모듈성 위반(Wong 외 2011), 형태의 일관성을 잃는 표류(Perry & Wolf 1992), 정적 분석으로 자주 발견되지 않는 설계 결함(Li 외 2021)이 그렇다. 클론, 평행한 형제 구현, 공유 관례로 규칙을 다 지키면서도 침식될 수 있다(노트의 추론).
- **모든 변경을 한 모듈에 가둘 수는 없다.** 공변경 클러스터의 약 48%는 문어형이고 개발자는 이를 정상으로 본다(Silva 외 2019; Silva 외 2015 [2차 출처]). 산재는 예외가 아니라 규칙이며(Eaddy 외 2008), 어떤 트리도 하나의 지배적 분해다(Tarr 외 1999).
- **표현 문제: 파일당 클래스 하나와 타입만 공개하는 규칙은 변형 축을 우선한다.** 연산 하나를 더하면 N 개 모듈을 편집하게 된다(Cook 2009에서의 노트의 추론).
- **기능 상호작용 코드는 두 기능 위의 모듈에 놓여야 하고, 상호작용 쌍마다 늘 수 있다**(Apel & Kästner 2009에서의 노트의 추론).
- **공유 인프라는 허브가 된다.** 0층의 패키지 전체 오류 enum 이나 퍼사드는 최대 영향 범위를 가진다(노트의 추론). 한곳에 모으라는 지침(Microsoft 2009)과 실패 단위 가까이 두라는 지침(Jewson 2023)이 갈린다.
- **명시적 맥락 전달 자체가 산재다.** ln-structure 와 맞는 방식이지만 Rhino 에서 가장 결함이 많았던 관심사가 바로 메서드마다 넘기는 범위 매개변수였다(Eaddy 외 2008).
- **책임을 먼저 고정한다.** 의존을 알기 전에 정한 설계 규칙은 가치 봉우리를 놓치고(Baldwin & Clark 2000 [2차 출처]), 가치 지형을 알 때까지 모듈화를 미루는 데에도 가치가 있다(Sullivan 외 2001).
- **공통 모듈 추출(역전)에는 비용이 있다.** 층이 늘수록 구조가 경직된다(Gamba & Fusari 2009). 하위 전용 import 와 같은 층 금지가 에이전트를 이른 공통 모듈 추출로 몰 수 있고, 추출된 모듈마다 가시성 비용이 있는 새 설계 규칙이 된다(노트의 추론).
- **구체 모듈의 표면에 기댄다.** 설계 규칙의 사례는 인터페이스 표준(Servlet API)이었고 그 덕에 구현 대체가 가능했다(LaMantia 외 2008). 구체 모듈의 표면은 공개 타입이 구현 결정을 새지 않을 때만 같은 역할을 한다(노트의 추론).
- **한 문장 시험은 쉽게 통과된다.** 같은 에이전트가 줄과 코드를 모두 쓰면 문법 시험은 쉽게 맞춘다(노트의 추론). 시험의 단서가 "completely"에 기대므로 줄과 내용의 대조가 필요하다(Stevens 외 1974).
- **구조 지표로 책임 하나를 강제하면 근거가 약하다.** 구조 응집 지표는 결함을 잘 예측하지 못하고(Basili 외 1996; Radjenović 외 2013), 크기에 교란되며(El Emam 외 2001), 서로 55% 어긋난다(Ó Cinnéide 외 2017).

### 열린 질문

- 책임 줄을 비밀 형식("X 를 숨긴다. X 가 바뀌면 이 모듈만 바뀐다")으로 쓰게 할 것인가, 단계형 줄을 lint 할 것인가(Parnas 1994; Bass 외 2003).
- 1974년 문법 시험(쉼표·"and"·동사 여럿, 시간어, all·manage·handle·util 같은 일반 목적어, initialize·clean-up 같은 생애 주기 단어)을 책임 줄 lint 로 만들 수 있는가. 줄과 모듈 내용의 일치는 어휘 유사도(C3 식)나 LLM 판정으로 볼 수 있는가. 검증 연구는 없다(Stevens 외 1974; Marcus 외 2008; Bavota 외 2013).
- 같은 에이전트가 책임 줄과 식별자를 모두 쓰면 어휘 기반 응집은 의미를 잃는가(굿하트 위험; 노트의 추론).
- `lnt doc` 이 층 지도와 따로 PCW 식 비밀 트리(주 비밀, 부 비밀, 숨은 하위 모듈 표시)를 내야 하는가. 자식 모듈의 책임이 부모의 책임을 겹침 없이 나누는지 검사할 수 있는가(Parnas 2009; Bredereke 2002 [2차 출처]).
- 공개 데이터 속성, 내보낸 형식 상수, 순서 약속 같은 의미 누출을 어떻게 탐지하는가(Parnas 2009; Parnas 1972).
- 정보 은닉 정리의 전제("사람은 무엇을 숨길지 안다")가 AI 에이전트에게도 성립하는가. 표면 강제로 충분한가(Parnas 2009).
- 계산된 층과 별도로 의도한 층(허용 사용의 상한)을 두어 표류를 알려야 하는가(Bachmann 외 2000).
- Parnas 의 네 기준을 에이전트가 더한 import 에 대한 리뷰 질문("이 간선이 유용한 부분 집합을 없애는가")으로 쓸 수 있는가(Parnas 1978).
- 타입 전용 import 와 진입점에서 연결된 구현을 uses 로 셀 것인가(Parnas 1978).
- 층을 가로질러야 하는 비밀(Habermann 외 1976 의 메모리 관리자)을 위한 허용 패턴이 필요한가.
- 팬인이 큰 모듈의 표면 변경을 리뷰 대상으로 표시하고(불안정 인터페이스의 정적 근사), 팬인과 팬아웃이 모두 큰 허브를 경고할 것인가(Mo 외 2021; Sturtevant 2013).
- 파일 단위가 아니라 표면 단위로 모듈 수준 DSM 지표(전파 비용, 가시성 팬인·팬아웃 범주, DL 류)를 계산해 시간에 따라 추적할 것인가(MacCormack 외 2006; Mo 외 2016).
- `lnt blast` 의 이력 보조판: 각 importer 가 실제로 함께 바뀐 빈도를 보이고, import 경로가 없거나 import 반대 방향인 반복 공변경을 Clio 처럼 표시할 것인가. 문헌의 설정은 지지도 2 이상·신뢰도 0.5 초과(Zimmermann 외 2003), 30개 넘는 항목을 건드린 변경 제외(Zimmermann 외 2005), 10개 넘는 패키지를 건드린 커밋 제외(Silva 외 2014), 최근 다섯 릴리스에서 두 번 이상 반복(Wong 외 2011)이다. 이력은 얼마나 필요한가(ROSE 는 프로젝트 시작 몇 주 뒤부터 쓸 만했고 Clio 는 다섯 릴리스를 봤다).
- 모듈을 건드린 커밋·이슈 텍스트를 그 모듈의 책임 줄과 비교할 수 있는가. 이슈 설명의 의미 유사도로 클러스터의 주제 일관성을 본 선례(Silva 외 2014)만 있다.
- 모듈 크기 상한은 정당한가. DL 의 5파일 기준은 약하고(Mo 외 2016), 1974년 논문은 실행문 5개 미만이나 100개 초과를 검토 대상으로만 제안했다(Stevens 외 1974).
- 하위 전용 import 와 같은 층 금지가 깊은 층 사슬과 이른 공통 모듈 추출을 낳는가. 층 깊이의 증가를 도구로 잴 수 있다(Parnas 1978; Gamba & Fusari 2009).
- 책임 줄이 모듈이 흡수하는 환경 변화(Sullivan 외 2001 의 환경 매개변수)를 함께 적어야 하는가.
- 모듈마다 예상 변화 축(변형 추가인가 연산 추가인가)을 선언해 에이전트가 변경이 국소적으로 남는 분해를 고르게 할 것인가(Cook 2009; Wadler 1998).
- 기능 상호작용 모듈과 팬인이 큰 퍼사드의 책임 줄은 어떻게 쓰는가(Apel & Kästner 2009).
- 물리 트리에 억지로 넣지 않고 관심사 태그나 관심사 지도 같은 가상 뷰로 기능을 추적하게 할 것인가(Tarr 외 1999; Apel & Kästner 2009).
- 이미 외부 퍼사드가 있는 인프라(표준 라이브러리 logging, log 크레이트, OpenTelemetry API)는 내부 모듈 없이 직접 쓰고 설정만 진입점에서 할 것인가(Python Logging HOWTO; Rust log 0.4.34; OpenTelemetry 문서).
- AI 저작이 비용 모형을 바꾸는가. 다시 쓰기가 싸면 인터페이스 변경이 주된 비용이 되어 더 적고 깊은 모듈 쪽이 유리한가(Parnas 2009 의 "easily replaced"). 실험이 싸면 순옵션가치 모형의 최적 실험 수가 늘어나 안정된 표면의 가치가 커지는가(Sullivan 외 2001). 흩어진 지점을 찾기는 싸도 N 곳의 일관성 유지는 여전히 비싼가(Eaddy 외 2008). 노트에는 근거가 없다.
- 에이전트의 커밋 습관(작업 하나에 커밋 하나, 큰 다관심사 커밋)이 공변경 신호를 깨끗하게 하는가 흐리는가. 커밋 정책은 결합을 지우거나 부풀린다(Zimmermann 외 2003 의 Mozilla 사례).
- ln-structure 경계가 변경을 실제로 더 잘 가두는가. 공변경 클러스터의 갇힘 비율(Silva 외 2019)과 진화적 결합 지수(Zimmermann 외 2003)로 비교할 수 있다.
- 반복 공변경 상대가 하위 모듈이면 합칠 후보인가, 아니면 하위 모듈의 책임이 사실상 그 단일 클라이언트로 정의된다는 신호인가(Wong 외 2011; 노트의 추론).
- 이 결과들이 Python(정적 추출기가 놓치는 동적 import)과 Rust(트레이트, impl 배치)로 옮겨지는가. 노트의 자료는 모두 Java, C, C++, C#, FORTRAN 이고 AI 가 쓴 코드에 대한 연구는 없다.

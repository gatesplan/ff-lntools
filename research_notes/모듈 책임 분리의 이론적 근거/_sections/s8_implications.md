## 9. ln-structure 에 주는 시사점

2~5장과 7~8장이 남긴 ln-structure 시사점을 규칙별로 모으고, 각 '도전'을 현재 프로토콜 문서(공통, Python, Rust)와 lnt 0.8.0 소스에 대어 확인했다. 근거의 강도는 형식 논증, 실증, 전문가 의견, 공급자 주장, 도구·컴파일러 동작으로 적었고 각 장이 매긴 것보다 올리지 않았다. 의존을 아래로만 흐르게 하는 골격(계산된 층, 모듈 간 비순환, 표면 경유 import, 진입점에서만 하는 연결, import 부수효과 등록 금지, 편집마다 도는 결정적 검사)은 여러 관점이 받친다. 객체 기반 관례(1파일 1클래스, 타입만 공개, 함수는 메서드로)는 BDE 표준 말고는 받치는 출처가 없고 Python·Rust 관용과 부딪힌다. import 그래프 밖의 결합(의미, 공변경)은 이 규칙들이 보지 못하고, 규칙들이 에이전트의 결과를 낫게 하는지는 어느 장도 재지 못했다. 곁 파일이 규칙을 잘못 읽은 곳은 **바로잡음**으로 표시했다. 이 장은 후보만 내고 결정은 사용자에게 남긴다.

### 9.1 뒷받침하는 것: 골격은 넓게, 객체 기반 관례는 좁게 받친다

**책임 한 줄과 사람이 정하는 책임.** 모듈은 서브프로그램이 아니라 책임 할당이고(Parnas 1972 §2.1), 안내서에는 비밀만 적으며(Parnas 2009 §2.1), 모듈의 기능은 구현이 아니라 변환을 묘사하는 구로 쓴다(Stevens 외 1974 §2.3). CRC 의 '어떻게가 아니라 무엇'(Beck & Cunningham 1989 §3.1), 수단을 말하지 않는 이름(Evans 2015 §4.1), 코드맵(Kladov 2021a §8.4)도 같다. 책임을 겹치지 말라는 RDD 와 DRY 는 '책임으로 써 보면 같은 일을 맡은 모듈이 드러난다'는 문장을 받친다(§3.1, §3.4). 강도: 전문가 의견, 형식 논증. 줄의 효과를 잰 연구는 없다.

**의존으로 계산하는 층.** 층 공식은 Parnas(1978)의 층 정의, Lakos(1996 [2차 출처])의 수준과 같다(번호만 하나 밀림, §2.2, §4.3). 계산된 수준에서는 같은 층 의존이 정의상 생기지 않고(§4.3, §5.6), 아래 어느 층이든 허용하는 것은 '엄격한 방식은 실무상 어렵다'(Knoernschild 2012 §4.3)와 맞는다. 같은 층 모듈의 독립은 설계 규칙 위계의 성질이고, 같은 층을 맡은 개발자끼리는 소통이 적었다(Xiao 외 2014; Wong 외 2009 §2.4). 강도: 형식 논증, 전문가 의견, 실증(한 프로젝트). 수준화 자체의 이점을 시험한 실증은 없다(§4.3).

**모듈 간 순환 금지, 모듈 안 순환 허용.** 순환이 없어야 층마다 시험할 부분 집합이 생긴다(Parnas 1978 §2.2). 모듈을 가로지르는 순환은 강한 결함 패턴이었고(Mo 외 2015), 순환을 품은 핵심부 파일은 결함이 3.4배였다(Sturtevant 2013 §2.4). Dropbox 는 순환을 끊은 일을 '아마' 프로젝트에서 전략적으로 가장 효과적인 부분이라 했다(Sanguansin & Shah 2021 §7.5). 단위 사이는 비순환, 단위 안은 자유라는 모양은 Go, JPMS, Cargo 와 같고(§5.6, §8.1), Lakos 도 한 컴포넌트 안의 순환은 허용한다(§4.3). 강도: 실증(상관, Java·C·C++), 도구·컴파일러 동작, 전문가 의견.

**표면으로만 import 와 맨 위 층 공개.** 모듈 전체를 이름으로 가리키는 연결이 결합이 낮고(Stevens 외 1974 §2.3), 설계 규칙에만 의존하는 모듈이 숨은 모듈이다(Sullivan 외 2001 §2.4). 공개 면적을 의도에 맞추고 도구로 강제하라는 Brown(2015)과 Google(Winters 외 2020)도 같은 쪽이다(§4.1, §4.5). PEP 8 이 인정하는 구조적 공개 통로는 하위 모듈을 드러내는 패키지 `__init__` 하나다(§7.1). Rust 는 `pub use` 로 내부와 다른 구조를 드러내라 하고(Book 7.4), 깊은 경로는 E0603, `pub(crate)` 누출은 E0364 로 막히며, '꺼내 주기'는 `unnameable_types` 의 처방과 같다(§8.1, §8.2). 에이전트 실험에서는 의존 파일의 구현을 지우고 시그니처만 남겨도 완성 정확도가 크게 떨어지지 않았고(Zhang 외 2024), 뼈대가 전체 파일보다 위치를 잘 찾았다(Xia 외 2024 §5.4). 모든 파일을 읽을 수 있는 에이전트에게 표면은 "프로그래머가 정보를 쓰지 않기로 결정하리라 기대해서는 안 된다"(Parnas 1971 [2차 출처])는 통제를 대신한다(2장 곁 파일의 추론). 강도: 전문가 의견(공식 문서 포함), 도구·컴파일러 동작, 실증(중간).

**상위 호출 해결 순서와 의존성 역전.** 네 단계는 Lakos 의 올리기, 내리기, 함께 두기, 콜백에 대응하고, 콜백의 필요는 나쁜 구조의 증상일 수 있다는 경고가 역전을 마지막에 둔다(Lakos 1996 [2차 출처]; Lakos 2016 §4.3). 1:1 합치기는 양방향으로 함께 쓰이면 합치라는 Ousterhout(§3.3)와 맞는다. 역전을 아끼라는 데에는 출처가 일치한다. Larman(2001)은 "pick your battles"라 했고, Khononov(n.d.)는 거리나 변동성이 클 때만 계약을 두라 하며(§3.6), Python 실무는 DI 를 의심하고 역전이 국소 복잡도를 더한다고 본다(Percival & Gregory 2020; Seddon 2023 §7.4, §7.5). 명시 상속은 검사기가 구현을 정의 지점에서 검증하게 하고(typing spec §7.3), 진입점에서만 하는 연결은 조합 루트와 같다(Seemann 2011 §4.2). 강도: 전문가 의견, 조직 경험 보고.

**import 부수효과 등록 금지.** 가장 넓게 받쳐진다. PEP 810 은 명시적 발견을 권하고, Meta 의 Cinder strict modules 는 데코레이터 레지스트리를 막았으며(현재 지위 [미확인]), 지연 import 를 도입하자 암묵적 등록에 기댄 코드가 깨졌다(Méndez Bravo 2024 §7.2, §7.5). Google 지침과 PyPA entry point 도 같은 쪽이다(§7.4). 이론으로는 구성 요소가 누가 자기를 쓰는지 알 필요가 없고(Parnas 1978 §2.2), 발행-구독 결합은 구문에 보이지 않는다(Cataldo 외 2009 §2.5). 강도: 전문가 의견(공식 문서 포함), 조직 경험 보고, 형식 논증.

**1파일 1클래스, 타입만 공개, 함수는 메서드로.** 직접 선례는 BDE 하나다. 외부에 쓰이는 클래스마다 컴포넌트를 두고, 이름공간에는 클래스와 연산자만 두며 함수는 Util 클래스에 넣는다(Bloomberg 2026 §4.3). 파일 단위 공변경 분석이 클래스 단위와 같아진다는 점(§2.5)은 추론이다. Rust 에서는 생성자와 수신자가 분명한 연산을 연관 함수로 두는 부분만 공식 지침과 맞는다(C-METHOD, C-CTOR §8.4). 강도: 코딩 표준 하나와 추론.

**Rust 세부.** C6 의 근거('메서드 호출에는 `use` 가 필요 없다')는 Reference 의 메서드 조회 규칙 그대로다. RFC 155 가 같은 규칙을 둔 적이 있고, 이를 되돌린 RFC 735 도 '메서드 정의를 찾는 쉬움'을 잃는다고 인정했다(§8.3). `mod.rs` 표면은 RFC 2126 이 폐기하지 않은 방식이고(§8.4), `pub(crate)` 를 표면 밖에 두는 것은 C-HIDDEN 과 맞는다(§8.2). `Box<dyn Trait>` 기본은 경계에 제네릭을 두지 말라는 Kladov(2021c)와 단형화 비용(Anderson 2020a)이 받치고, 모듈 비순환은 크레이트 승격을 싸게 한다(Anderson 2020b §8.3). 강도: 도구·컴파일러 동작, 언어 설계 선례, 전문가 의견.

**Python 세부.** PEP 8 은 복잡한 패키지 구조에서 상대 import 를 받아들이고, PEP 328 의 근거(하위 패키지를 고치지 않고 구조를 바꾸기)는 층 사이를 옮겨 다니는 모듈 폴더와 맞는다(§7.1). 지연 표면은 PEP 562 가 드는 주 용도이고, `from ..lX import Foo` 는 import 지점에서 `__getattr__` 를 불러 실패가 그 자리에서 드러난다(§7.2). `TYPE_CHECKING` import 를 의존으로 세는 것은 import-linter 의 기본값과 같다(§7.5). 강도: 전문가 의견(공식 문서), 도구 동작.

**훅으로 편집마다 검사하고 해결 방법을 돌려줌.** 편집 시점 린트를 빼자 SWE-agent 의 해결률이 18.0% 에서 15.0% 로 내려갔다(Yang 외 2024 §5.4). 공급자 문서는 훅은 결정적이고 CLAUDE.md 는 권고라 하고(Anthropic 2026a), 도구의 오류 응답은 구체적이고 실행 가능하게 쓰라 한다(Aizawa 2025 §5.5). 냄새는 대부분 코드가 처음 생길 때 들어와 약 80% 가 살아남았고(Tufano 외 2015 [2차 출처]), 에이전트가 구조를 스스로 가꾼다는 근거는 없었다(Horikawa 외 2025 §4.4; He 외 2026 §5.4). Kraken 은 층을 말로만 해서는 부족했다고 했다(Seddon 2023 §7.5). 강도: 실증 1건(중간), 공급자 주장, 조직 경험 보고.

**모듈 지도, `lnt blast`, `lnt review`.** 모듈 안내서는 모두가 읽는 유일한 문서이고(Parnas 2009 §2.1), 공급자도 코드베이스 지도와 아키텍처 결정을 문맥에 넣으라고 한다(Anthropic 2026a; 2026d §5.5). blast 는 조정 요구, 전파 비용과 같은 관심이다(Cataldo 외 2006 §5.3; MacCormack 외 2006 §2.4). review 를 판정이 아닌 질문으로 두는 것은 냄새가 그 자체로 나쁘지 않고 판단은 설계자 몫이라는 쪽(Fowler 2006; Tsantalis & Chatzigeorgiou 2009 §4.4)과 맞는다. 강도: 전문가 의견, 공급자 주장. 지도에 대한 측정은 오히려 반대 쪽에 있다(9.2).

### 9.2 도전하거나 어긋나는 것: import 그래프 밖의 결합과 언어 관용

**책임 한 줄.** '무엇을 맡는가'와 '무엇을 숨기고 어떤 변경을 가두는가'는 다르다. "입력 파싱을 맡는다" 같은 단계형 줄도 지금 기준을 통과하는데, Parnas 는 이를 "how to …" 비밀의 오용으로 보았고(Parnas 1994 §2.1), Löwy 와 Evans 는 변경의 축을 경계의 증거로 쓴다(Löwy 2019; Evans 2015 §4.1). 프로토콜의 예시 줄(값으로 나타낸다, 상태를 맡는다)은 데이터와 연산을 함께 두는 Parnas(1972) 쪽으로 읽히는데(이 장의 해석), 1974년 척도로는 그런 묶음이 기능적보다 낮은 통신적 결속이다(§2.3). 어느 이론에 기대는지는 문서에 없다. Martin 의 행위자 기준으로는 줄을 통과한 모듈도 SRP 위반일 수 있다(Martin 2017 [2차 출처] §3.2). 같은 에이전트가 줄과 코드를 함께 쓰면 문장 시험은 쉽게 통과된다(§2.3). 강도: 형식 논증, 전문가 의견.

**세분도.** 비밀이 독립적으로 바뀔 때만 나누고(Parnas 2009 §2.1), 지나친 분리는 모자란 분리만큼 나쁘며(Tarr 외 1999 §2.6), 과분할이 실제 실패라는 데에는 Martin 도 동의한다(Ousterhout & Martin 2025 §3.3). 에이전트에게는 세 파일 이상을 고치는 과업의 성공률이 10% 아래였고(Rashid 외 2025 §5.4), 파일을 나누자 변경당 추정 입력 토큰은 약 83% 줄었지만 변경당 시간은 342초에서 454초로 늘었다(Edwards-Alexander 2026 §5.5). 둘 다 교란이 있고 모듈이 아니라 파일을 센다. **바로잡음.** 3장 곁 파일은 늘 함께 바뀌는 모듈을 합치라는 지침이 없다고 했지만, 해결 순서 3 이 서로 부르고 늘 함께 바뀌는 1:1 짝을 합친다. 빠진 것은 서로 부르지 않으면서 함께 바뀌는 모듈의 기준이다.

**계산된 층과 같은 층 금지.** **바로잡음.** 2장과 4장 곁 파일은 ln 이 층을 선언하지 않으므로 의도하지 않은 import 가 '조용한 재수준화'로 흡수된다고 했다. 실제로는 폴더가 선언 층이다. 같은 층이나 위 층 import 는 C1, 선언 층과 계산 층의 불일치는 C3 이 되어 훅이 곧바로 알린다. 남는 도전은 둘이다. 층을 바꾸지 않는 아래 층 import 는 무엇이든 검사 없이 들어온다. 층을 바꾸는 import 에도 C1 풀이의 첫째와 C3 메시지가 층 올리기(`lnt move`)라서 의도한 의존과 그렇지 않은 의존을 가르지 않는다. 허용 사용 관계나 허용 의존을 선언하게 하는 V&B, BDE, import-linter 와 다른 점이다(Bachmann 외 2000 §2.2; §4.3; §7.5). 의미와 안정성에 따른 방향도 보지 않는다. 순수 코어는 입출력을 import 하지 않는다는 제약(Seemann 2018 §4.2)과 SDP(Martin 2000 §3.2)는 import 깊이로 표현되지 않고, 표준 라이브러리 입출력은 외부 의존이 아니어서 효과가 있는 모듈도 l0 에 놓인다(§4.2). 가장 강한 결함 패턴인 불안정 인터페이스는 비순환 그래프에도 생긴다(Mo 외 2021 §2.4). 같은 층 금지는 표준 층 규칙이 아니고(Bachmann 외 2000 §2.2; Sangal 외 2005 §5.6), 산업용 층 검사기도 같은 층을 허용한다(§4.5). 계산된 수준에서는 그래프 모양에 대한 추가 제약이 아니지만, 층이 경로에 들어 있으므로 같은 층 import 가 곧 폴더 이동이 된다(§4.3). 그래서 'strict layering'이 아니라 수준화라 불러야 맞다(§5.6). 폴더를 계산된 층에 묶은 도구는 검토한 것 중 없고, 이동의 빈도와 비용은 알려지지 않았다(§5.6). `lnt move` 가 import 를 고치므로 기계적 비용은 작지만, 의존을 빼 계산 층이 내려가도 C3 이므로 폴더는 양방향으로 움직인다. **바로잡음.** 2장과 3장 곁 파일은 같은 층 금지가 이른 공통 모듈 추출을 강요한다고 했다. 그러나 첫 처방은 import 하는 쪽을 올리는 것이고, 떼어 내기는 두 모듈이 공통 부분 때문에 서로 기댈 때 쓴다. 남는 문제는 떼어 낼 조건에 '같은 지식인가'(Metz 2016 §3.4)가 없다는 점뿐이다.

**순환.** 실증은 혼재한다. 패키지 순환은 여섯 반패턴 가운데 영향이 가장 작았고(Mo 외 2021 §2.4), 순환의 위치나 종류로는 해로운 순환을 가를 수 없었다(Oyetoyan 외 2015 §4.4). 순환 금지를 제1원리에서 끌어낸 출처는 없다(§5.6, 5장 곁 파일). Rust 는 모듈 순환을 일부러 허용하므로(RFC 1560; 실험 R1; Kladov 2021d §8.1), ln 의 금지는 추적성과 크레이트 승격 같은 ln 자신의 목표로 정당화해야 한다. 모듈 안 순환에는 크기 상한이 없지만 Lakos 는 소수 클래스에만 허용한다(§4.3). Python 에서는 순환 안의 최상위 `from .a import A` 가 실패할 수 있는데 lnt 는 이를 보지 않는다(§7.2).

**표면과 맨 위 층 공개.** 인터페이스는 시그니처가 아니라 가정이므로 순서, 단위, 시점 같은 의미 누출은 표면 검사를 통과한다(Parnas 2009 §2.1). Shopify 의 비공개 검사는 문서 없는 공개 코드를 늘렸고 결국 제거되었다(McGibbon & Salzberg 2024 §4.5). 검사를 통과하려고 표면을 넓히는 에이전트도 같은 팽창을 낳을 수 있다. 5장 곁 파일이 확인을 미룬 '생성된 표면이 다 내보내는가'에는 프로토콜이 답한다. 모듈 표면은 밑줄 없는 클래스와 타입 별칭을 모두 내보내므로 모듈 수준의 기본값은 공개이고, 고르는 장치는 밑줄과 그 위 단계의 맨 위 층 규칙이다. 넘기기만 하는 메서드가 생긴다는 3장 곁 파일의 지적(Ousterhout 2018b §3.3)은 꺼내 주기를 고려하지 않았다. 타입은 꺼내 주기로 풀리고, 이 지적은 동작을 감싸는 메서드에만 남는다. `py.typed` 를 배포하면 밑줄 없는 내부 파일과 하위 모듈 이름이 검사기와 IDE 에 공개로 보인다(§7.1). Rust 의 공개 범위는 조상만 가리키므로 층 순서를 rustc 로 표현할 수 없고, 봉인 트레이트는 `unnameable_types` 에 걸려 숨은 타입 검사와 부딪힌다(§8.1, §8.2).

**역전과 연결.** 육각형과 양파 구조는 구동되는 협력자마다 역전하고 포트마다 시험용 어댑터를 둔다(Garrido de Paz 2018 §4.2). 시험 대역이 1:N 의 N 에 드는지는 정해져 있지 않다. 조합 루트는 라이브러리에 두지 않는다(Seemann 2011 §4.2). 부품 패키지에서 연결을 맡는 진입점이 맨 위 층인지 호스트 코드인지 문서에 없고, 패키지 밖 구현체에 명시 상속을 요구하면 호스트 쪽에 어댑터가 필요하다. PEP 544 는 명시 표시를 강요하는 것이 파이썬답지 않다며 구조적 타입을 들였고, 실무는 소비자 쪽 구조적 포트를 선호한다(Percival & Gregory 2020; Schlawack 2021 §7.3). 등록 금지도 생태계 전체의 합의는 아니어서, Effective Go 는 init 함수로 등록하는 `import _ "net/http/pprof"` 를 공식 관용으로 소개한다(§5.6). 강도: 전문가 의견.

**1파일 1클래스.** 이 규칙은 `lnt check` 위반이 아니라 `lnt review` 질문이다. Google 지침과 Stack Overflow 채택 답변이 반대하고, 원래 근거는 자바 컴파일러가 이름으로 파일을 찾는 편의였다(§7.6). 지지하는 Rust 자료도 없다(§8.4). Rust 의 공개 범위 경계는 파일 모듈이어서, C6 가 허용하는 대로 `impl T` 를 폴더의 다른 파일에 두면 T 의 비공개 필드가 보이지 않아 `pub(super)` 필드가 필요해진다(§8.3, 8장 곁 파일). 이해에 주는 효과를 잰 연구는 없다(§5.2).

**타입만 공개, 함수는 메서드로.** **바로잡음(범위).** 이 규칙은 '공개 이름' 절에 있고, lnt 는 다른 모듈이 표면에 없는 이름을 import 할 때만 C2 로 막는다. 모듈 안 파일끼리 쓰는 자유 함수와 전역은 검사하지 않는다. 따라서 7장과 8장 곁 파일의 반론은 경계를 넘는 함수에 한해 유효하고, 8장 곁 파일이 물은 '표면이 아닌 파일의 자유 함수 허용'은 도구가 이미 허용하는 것을 문서가 적지 않은 문제다. 그래도 반대 근거가 많다. Python FAQ 와 Google 지침은 정적 메서드 대신 모듈 함수를 권하고, Ronacher(2025)는 에이전트에게도 클래스보다 함수를 권한다(§7.6). Rust 공식 문서는 자유 함수를 부모 모듈 경로로 부르는 것을 관용으로 소개하고, rust-analyzer 는 'doer' 객체를 피하라고 한다(§8.4). 검토한 언어나 도구 가운데 타입만 내보내게 하는 것은 없다(§5.6). 이런 자료로 학습한 에이전트와 린터가 규칙을 '고치려' 들 수 있다(§7.6 의 추론).

**Python 세부.** 상대 import 는 Google 지침이 금지하고, PEP 8 은 절대 import 를 기본으로 두되 프로젝트 지침의 우선을 인정한다. Ruff TID252 를 켠 호스트와는 부딪힌다(§7.1, §7.5). `TypeAlias` 는 3.12 부터 deprecated 이고 spec 이 인정하는 재노출은 `from Y import X as X` 다. 린터나 에이전트가 `type` 문으로 '고치면' 결과가 클래스가 아니어서 상속이 깨진다(§7.1). `TYPE_CHECKING` import 를 세는 것은 가드를 정당한 순환 해법으로 다루는 PEP 들보다 엄격한 설계 선택이다(§7.2). lnt 는 `ast` 로 읽으므로(9.3) 문자열 경로나 `importlib` 로 만든 의존은 보지 못한다(7장 곁 파일).

**Rust 세부.** Rust 는 C6 와 같은 규칙(RFC 155)을 1년도 안 되어 RFC 735 로 되돌렸다. 이유는 DRY 를 어기는 일회용 확장 트레이트와, 원래 동기였던 구현 세부가 사라진 것이었다. RFC 445 가 늘어난 import 를 덜려고 권한 glob 프렐류드는 이름을 하나씩 적는 표면과 맞지 않는다(§8.3). 그러므로 C6 는 늘어난 import 를 드러난 간선으로 보는 ln 의 목표로 정당화해야 한다. `impl Display for Wrapper<Local>` 의 소속 모듈은 프로토콜에 없다(§8.3, 구현의 동작은 9.3). `mod.rs` 표면은 공식 권장인 `name.rs` 와 다르고, 생성 코드의 `pub` 표기는 `unreachable_pub` 와 `redundant_pub_crate` 를 함께 만족할 수 없다(§8.4, §8.5). `Box<dyn Trait>` 기본은 dyn 호환이 아닌 트레이트 안 `async fn` 을 담지 못하고(Mandry 2023), 비공개 필드만 둔 타입은 바깥에서 메서드마다 값 전체를 빌리게 해 `RefCell` 로 물러서게 할 수 있다(Matsakis 2021 §8.3, 8장 곁 파일의 추론). 실무의 단단한 경계는 크레이트인데, ln 은 크레이트가 주는 것 가운데 비순환만 컴파일러 밖에서 다시 구현한다(Kladov 2021b §8.4).

**편집마다 검사.** 최전선 모델은 하네스 없이도 10/10 을 통과했고 하네스는 토큰을 약 10배 썼다(Jain 2026 §5.5, 그 하네스에 린터나 훅은 없었다). 공급자는 모델이 바뀌면 규칙을 다시 보라고 한다(Anthropic 2026c §5.5). 성숙한 검사기는 모두 기준선이나 예외 장치를 두는데(§5.6) lnt 에는 없다(9.3). Shopify 에서는 무시 목록이 불어나고 고침이 부자연스럽고 지나치게 복잡해졌다(§4.5). 막힌 에이전트가 역전을 남용하거나 코드를 옮겨 규칙만 맞출 수 있지만 자료는 없다. 기계적 강제가 좋은 분리를 만든다는 출처도 없다(§4.5). **바로잡음(작음).** 5장 곁 파일은 훅이 진행을 막는다고 했지만, PostToolUse 훅은 편집을 되돌리지 않고 exit 2 와 함께 위반과 풀이를 돌려준다.

**모듈 지도.** 가장 큰 통제 평가에서 LLM 이 만든 문맥 파일은 8개 설정 중 5개에서 성공률을 낮췄고 개발자 파일도 +2.4%(p = 0.21)에 그쳤다. Claude Code 와 Sonnet-4.5 는 파일 없이 73.2%, 개발자 파일로 70.3%, LLM 파일로 65.2% 를 풀었고, 개요는 수정할 파일에 처음 닿기까지의 단계를 줄이지 못했다. 비표준 관행을 정하는 지시는 지켜졌다(Gloaguen 외 2026 §5.4). **바로잡음.** 5장 곁 파일은 ln 의 지도를 '도구가 계산한 한 줄'이라 했지만, 계산되는 것은 목록과 층이고 줄은 사람이 정하는 스펙이다. 시험된 적이 없으므로 입증 책임은 지도 쪽에 있다. 입력 길이만으로도 성능이 13.9~85% 떨어지는데(Du 외 2025 §5.4) 지도는 모듈 수에 비례해 커진다.

**`lnt blast` 와 `lnt review`.** blast 는 영향 범위가 아니라 정적 도달 범위를 보인다. 두 회사에서 구문 의존의 74.3% 와 97.3% 는 함께 바뀐 적이 없었고(Cataldo 외 2009), Hadoop 의 확인된 위반 152건 중 66건은 명시적 의존이 없거나 반대 방향으로만 있는 결합이었다(Wong 외 2011 §2.5). import 그래프 도구는 냄새 목록의 약 3분의 1 만 덮고, 우회 의존의 예측력을 다룬 연구는 없다(§4.4). 강도: 실증(상관).

### 9.3 이 세션에서 직접 확인한 것: 지연 표면은 타입 검사기에 `Any` 로 보인다

**지연 표면과 타입 검사기(조정자 확인, 2026-10-18).** uv 의 Python 3.14 와 PyPI 의 현행 mypy, pyright 로 확인했다. ff-lntools 의 층 표면과 패키지 표면은 `_EXPORTS` 딕셔너리, `__all__ = list(_EXPORTS)`, 모듈 `__getattr__` 로 된 지연 꼴이다. 여기서 가져온 이름(`from lntools.l1 import Graph`, `from lntools import Cli`)은 두 검사기 모두 `Any` 로 보았고, 모듈 표면이 `from .graph import Graph` 로 내보낸 이름은 제 타입으로 보았다. 작은 시험 패키지의 지연 표면에 `if TYPE_CHECKING:` 블록과 `from .order import Order as Order` 를 더하자 두 검사기가 실제 타입을 풀어 일부러 넣은 타입 오류를 보고했다. 런타임 지연도 유지되어, 이름에 접근하기 전에는 하위 모듈이 로드되지 않았다. ff-lntools 의 코드는 87곳 모두 모듈 표면으로만 import 하므로 내부에는 영향이 없다. 타입을 잃는 것은 패키지 루트 표면으로 가져오는 소비자와, Python 프로토콜 문서의 예시처럼 층 단위로 가져오는 코드다. 7장 곁 파일이 [미시험]으로 남긴 지연 표면의 정적 가시성이 이로써 확인되었다. 스캐너와 문서 생성기가 이 블록을 만들고 세려면 무엇을 바꿔야 하는지는 확인하지 않았다.

**Rust 실험(8장, 2026-10-18).** 실험 R1(rustc·cargo 1.99.0, edition 2024)에서 서로 `use` 하는 두 모듈은 진단 없이 컴파일되었고, 다른 모듈에 둔 고유 impl 도 컴파일되었다. `pub(crate)` 항목의 `pub use` 는 E0364, 서로 의존하는 두 path 패키지는 순환 오류였고, `unnameable_types` 를 켜자 봉인 트레이트가 경고를 냈다. 실험 R2 는 ff-lntools 의 `tests/fixtures/rust_clean` 사본(층 l0~l3, `mod.rs` 표면 15개)을 cargo 1.99.0, Clippy 0.1.99 로 검사했다.

| 설정 | 결과 |
|---|---|
| 생성된 그대로 | 경고 0건 |
| `allow-private-module-inception` 제거 | `module_inception` 8건 |
| 층 표면의 `#![allow(unused_imports)]` 제거 | `unused_imports` 6건 |
| `-W unreachable_pub` | 31건 (`unnameable_types` 0건, `missing_docs` 3건) |
| restriction·nursery 린트 열 개 | `missing_docs_in_private_items` 46, `pub_use` 20, `mod_module_files` 15, `redundant_pub_crate` 9. `self_named_module_files`, `inline_modules`, `module_name_repetitions`, `multiple_inherent_impl`, `wildcard_imports`, `absolute_paths` 는 0 |

`redundant_pub_crate` 는 린트 설명과 달리 크레이트 루트의 비공개 모듈에서도 발동했다.

**바로잡음의 근거로 읽은 lnt 0.8.0 소스(이 장, 실행하지 않음).** 같은 층이나 위 층 import 는 C1, 선언 층과 계산 층의 불일치는 C3 이다. C3 메시지는 계산 층으로 옮기는 `lnt move` 를 주고 계산 층이 낮아져도 나며, C1 풀이에는 해결 순서 네 단계가 실린다. PostToolUse 훅은 편집한 파일을 품은 모듈들의 위반만 exit 2 로 돌려주고, 세션 시작 훅은 src 아래 모든 ln 패키지의 지도를 넣는다. 위반을 면제하거나 기준선으로 묶는 장치는 없다. 1파일 1클래스는 `lnt review` 에만 있고, 함수와 상수는 다른 모듈이 import 할 때만 C2 로 걸린다. Python import 는 `ast` 로 읽고 함수 안 import 도 센다. `TYPE_CHECKING` 안 import 는 층 계산에 들어가고, 표준 라이브러리 밖 패키지(`typing_extensions` 포함)를 런타임에 import 한 모듈은 l1 이상이 된다. Rust C6 는 `Wrapper<Local>` 를 바깥 타입(`Wrapper`)의 모듈 소속으로 본다.

### 9.4 검토할 거리: 작은 수정 셋을 먼저, 설계 결정은 근거를 만들며

꽂아 쓰는 부품 패키지를 에이전트가 결정적 검사 아래에서 쓴다는 목표에 비추어 기대 가치가 큰 순서로 놓았다. 기준 번호는 프로토콜의 판단 기준이다. (1) ln-structure 의 의도, (2) 코딩 에이전트에게 자연스럽고 효율적인가, (3) 널리 인정되는 원칙.

1. **지연 표면을 타입 검사기가 보게 한다.** [분명하고 작은 수정] 무엇: `lnt doc` 이 층, 중첩 모듈, 패키지 표면에 `if TYPE_CHECKING:` 블록의 `from .x import Name as Name` 을 함께 쓴다. 그 전까지는 패키지 안에서 모듈 표면 import 를 권한다. 왜: 지금은 `Any` 이고, 이 블록으로 지연을 유지한 채 타입이 보였다(9.3). 부품 패키지 소비자의 주 경로인 패키지 루트 표면이 지금 타입을 잃는다. 비용과 위험: 이름 목록이 두 번 생성되지만 생성기는 하나다. 스캐너가 이 블록을 표면 안 코드로 세지 않는지는 확인하지 않았다. 기준: (1) 표면은 계약, (2) 타입 오류가 바로 보인다, (3) 명시적 의존.

2. **프로토콜 문구를 도구 동작에 맞춘다.** [분명하고 작은 수정] 무엇: (a) 함수·상수 규칙은 모듈 경계를 넘는 이름에만 걸린다(모듈 안 자유 함수를 허용으로 적을지는 따로 정한다). (b) 폴더 층은 계산 층과 같아야 해서 계산 층이 내려가도 옮긴다. (c) 1파일 1클래스는 review 질문이다. (d) C6 에서 제네릭 타입은 바깥 타입 소속이다. (e) `TYPE_CHECKING` import 를 세는 이유(가드 안에 의존을 숨기지 못하게)를 적는다. (f) import 는 막아도 코드 읽기는 막지 않는다(Colfer & Baldwin 2016 §5.3). 왜: 에이전트는 문서를 글자대로 따르고(판단 기준 2), 9.2 의 바로잡음에서 보듯 달리 읽힐 여지가 있다. 비용과 위험: 작다. (a) 를 허용으로 적으면 객체 기반 의도가 약해 보일 수 있다. 기준: (2), (1).

3. **TypeAlias 꺼내기 꼴을 시험하고 고른다.** [분명하고 작은 수정, 시험 먼저] 무엇: `from ...l1.eval import Env as Env` 와 지금의 `Env: TypeAlias = _Env` 를 9.3 과 같은 방법으로 비교하고, 재노출 꼴이 같거나 나으면 맨 위 층의 `as` 재노출을 공개 이름으로 센다(Rust `pub use` 처럼). 왜: deprecated 표시를 보고 `type` 문으로 바꾸면 런타임이 깨지고, 별칭 대입은 spec 의 재노출 꼴이 아니다(§7.1). 비용과 위험: Python 갈래는 import 한 이름을 표면으로 보지 않으므로 표면 읽기와 C2 를 고쳐야 한다. 검사기 동작은 [미시험]이다. 기준: (2), (3).

4. **책임 한 줄의 쓰는 법과 검사.** [설계 결정] 무엇: (a) 숨기는 결정이나 가두는 변경을 덧붙인다("X 가 바뀌어도 이 모듈만 바뀐다")(Parnas 2009; Löwy 2019). (b) 1974년 문장 시험을 한국어 결정적 검사로 만든다. 대상은 접속 표지(그리고, 또는, ~하고, ~거나, 쉼표), 시간어, 대상 없는 일반어(관리, 처리), 생애 주기어(초기화, 정리)다(Stevens 외 1974; Metz 2012 [2차 출처]). (c) 길이 상한과 CRC 처방(더 높은 수준으로 다시 쓰고, 안 되면 나눈다)을 둔다(Beck & Cunningham 1989). (d) 줄과 코드의 대조는 LLM 판정으로 review 에만 둔다. 왜: 사람이 정하는 유일한 입력이고 매 세션 지도에 실리는데, 지금 기준은 같은 에이전트가 쉽게 통과한다(§2.3). 비용과 위험: 시험의 신뢰도를 잰 연구가 없고 한국어 검사의 오탐률도 모른다. LLM 판정은 결정성(기준 2)에 어긋나 훅에 둘 수 없고 환각도 걸러야 한다(MM-assist 2025 §4.4). 기준: (1), (3) 정보 은닉, (2).

5. **함수는 메서드로, 공개는 타입만.** [설계 결정] 무엇: 유지하고 근거(에이전트에게 한 가지 꼴, 단순한 표면 생성)를 적거나, 경계를 넘는 자유 함수를 표면 이름으로 허용하거나, 상수만 완화한다. 왜: Python 과 Rust 의 공식·실무 지침이 반대쪽이고 찬성 쪽은 BDE 하나다(§4.3, §7.6, §8.4). AST 로 공개 이름을 고르기 쉽다는 근거는 최상위 `def` 에도 성립한다(§7.6 의 추론). 비용과 위험: 바꾸면 표면 생성, C2, review 가 함수를 다뤄야 하고 기존 패키지를 고쳐야 한다. 두면 관용을 학습한 에이전트·린터와의 마찰이 남는다. 어느 쪽이든 효과 자료는 없다. 기준: (2) 와 (3) 이 갈린다.

6. **자체 평가 장치.** [설계 결정] 무엇: 같은 명세를 ln 규칙·지도·훅이 있을 때와 없을 때 에이전트에게 만들게 하고, 성공률, 수정할 파일에 처음 닿기까지의 단계, 토큰, 변경당 파일 수, 층 이동 횟수를 잰다(Gloaguen 외 2026 등의 지표, §5.4, §5.5). 왜: ln 같은 분해가 결과를 낫게 한다는 통제된 증거가 없고(§3.6, §5.4), 9.5 의 질문 여럿을 이것 하나로 시험할 수 있다. 비용과 위험: 과업 설계와 반복 실행에 비용이 들고, 모델이 바뀌면 결과가 낡는다. 기준: 세 기준 모두에 근거를 만든다.

7. **의미와 안정성에 따른 방향 점검.** [설계 결정] 무엇: 층이 아니라 모듈 속성이나 review 질문으로 다룬다. (a) 시계, 난수, 네트워크 같은 효과 import 를 보이고, 순수로 표시한 모듈의 그런 import 를 알린다(§4.2). (b) 팬인이 큰 모듈의 표면 변경을 review 에 올린다(Mo 외 2015; 2021). (c) SDP 위반을 자문으로 보인다(Martin 2000). (d) 중첩 모듈마다 허용 의존을 선언한다(§4.3). 왜: 9.2 의 '계산된 층' 항목. 비용과 위험: 층에는 의미가 없다는 공통 규칙 2 와 섞이면 안 된다. 사람이 표시하면 스펙이 늘고, 도구가 추정하면 오탐이 난다. 기준: (3) 에 맞고 (1) 과 긴장한다.

8. **1파일 1클래스의 남은 쟁점.** [설계 결정] 무엇: 2026-10-07 결정대로 review 질문으로 두되, BDE 의 함께 두기 예외 넷을 review 에서 뺄지, Rust 형제 파일 impl 을 위한 `pub(super)` 필드를 허용할지 정한다. 왜: 그 뒤에 나온 근거가 여러 파일에 걸친 변경의 비용(§5.4)과 Rust 의 파일 단위 공개 범위(§8.3)다. 비용과 위험: 예외가 늘면 판단할 거리도 는다. 기준: (1), (2).

9. **C6 재검토.** [설계 결정] 무엇: 유지하고 RFC 735 의 반론에 대한 답을 문서에 적거나, 제네릭의 소속을 '이 모듈이 크레이트라면 고아 규칙을 만족하는가'로 정하거나(8장 곁 파일의 제안), 고유 impl 만 완화한다. 왜: Rust 는 같은 규칙을 되돌렸지만, C6 의 근거는 컴파일러의 메서드 조회 규칙 그대로다(§8.3). 비용과 위험: 완화하면 `lnt blast` 가 메서드를 거친 영향을 놓치고, 유지하면 일회용 확장 트레이트가 늘 수 있다. 기준: (1)(3) 은 유지 쪽, 생태계 관례는 완화 쪽이다.

10. **공변경 이력의 사용.** [설계 결정] 무엇: `lnt blast` 에 의존자마다 실제로 함께 바뀐 빈도를 덧붙이고, import 없이 반복해서 함께 바뀌는 모듈 쌍을 review 에 올린다(Wong 외 2011). 문헌의 설정은 지지도 2 이상·신뢰도 0.5 초과(Zimmermann 외 2003), 30개 넘는 항목을 건드린 변경 제외(Zimmermann 외 2005)다(§2.5, 2장 곁 파일). 왜: 가장 예측력 있는 신호는 이력이 있어야 보인다(§4.4). 비용과 위험: 새 패키지는 이력이 짧고 커밋 습관이 신호를 흐린다. 같은 코드에 다른 결과가 나오므로 훅이 아니라 정보와 review 에만 둔다. 기준: (3), (1).

11. **워크스페이스와 크레이트를 경계로.** [설계 결정] 무엇: 언제 중첩 모듈이나 층을 크레이트로 올릴지, lnt 가 워크스페이스를 다룰지 정한다(Kladov 2021b). 왜: 실무의 단단한 경계는 크레이트이고(§8.4), 모듈 비순환은 크레이트 승격을 싸게 한다(§8.3). 비용과 위험: 부품 패키지는 대개 라이브러리 크레이트 하나라 당장 이득이 작고, 크레이트를 나누면 관련 기능이 흩어진다(rustc-dev-guide; Tokio 2019 §8.4). 기준: (1), (3).

### 9.5 열린 질문

1. 보편 수준화(같은 층 금지)가 '느슨한 층 + 고른 형제 독립'보다 결합과 침식을 줄이는가(§2.2, §4.3, §5.6, §7.5).
2. 층 이동은 얼마나 자주, 어떤 비용으로 생기는가. 폴더의 층 번호는 에이전트의 길찾기를 돕는가, 흔드는가(§4.3, §5.6, §7.5).
3. 한 줄 지도는 위치 찾기와 성공률을 낫게 하는가. 모듈이 늘면 계층화나 점진적 공개가 필요한가(§5.2, §5.4, §5.5).
4. 1파일 1클래스와 타입만 공개가 변경당 파일 수를 늘리는가. 성공률은 그 수를 따르는가(§5.4, §7.6, §8.4).
5. 편집 시점 차단은 단계와 토큰을 얼마나 늘리고 그만한 값을 하는가. 위반 메시지는 의도한 수정으로 이끄는가, 역전 남용이나 코드 옮기기로 이끄는가. 모델이 좋아지면 어떤 규칙을 은퇴시키는가(§5.4, §5.5).
6. 시험 대역은 역전을 허가하는 두 번째 구현인가. 함수형 코어를 입출력의 기본형으로 둘 것인가. 코어와 셸 사이를 오가는 값 타입은 어디에 두는가(§4.2, §7.4).
7. 부품 패키지에서 연결을 맡는 진입점은 맨 위 층인가, 호스트 코드인가. 패키지 밖 구현체에도 명시 상속을 요구하는가(§4.2, §7.3).
8. 진입점에서 연결된 구현은 uses 인가. 3.15 의 `lazy` import 는 일반 import 로 세는가. 3.14 로 도는 lnt 가 이 구문을 어떻게 읽는지는 확인하지 않았다(§2.2, §4.3, §7.2).
9. 모듈 안 순환을 허용할 때 모듈이나 순환의 크기에 상한이 필요한가(§4.3, §7.5).
10. 층을 가로지르는 비밀과 정당한 횡단 관심(오류 처리, 설정)을 위한 허용 꼴이 필요한가(§2.2, §2.6, §5.1).
11. 우회 의존은 변경·결함 경향을 예측하는가. 한 줄 책임과 코드를 받은 LLM 은 다면 추상화를 믿을 만하게 짚는가(§4.4).
12. Rust: 의도적으로 이름을 숨긴 봉인 트레이트를 숨은 타입 검사에서 어떻게 빼고, `impl Trait` 반환은 어떻게 다루는가. 생성되는 `[lints]` 에 `self_named_module_files`·`inline_modules`(R2 에서 0건)를 켤 것인가. 비동기 주입 자리의 표준 꼴과 C5 경로 규칙은 무엇인가(§8.2~§8.5).
13. Python: `py.typed` 를 배포할 때 내부 파일과 층 폴더에 밑줄을 붙일 것인가. `typing_extensions` 를 외부 패키지로 셀 것인가. 지금은 외부로 세므로, 3.10–3.11 지원을 위해 여기서 `@override` 를 가져오는 모듈은 l1 이상이 된다(§7.1~§7.3).
14. 기존 코드에 도입할 때 기준선이 필요한가(§5.6, §7.5).
15. 사람의 인지 부하와 조정 비용으로 정당화된 원칙이 에이전트에게도 같은 무게를 갖는가. Java·C·C++ 에 몰린 실증이 AI 가 쓴 Python·Rust 부품 패키지에도 옮겨지는가(§2.7, §3.6, §5.2, §8.6).

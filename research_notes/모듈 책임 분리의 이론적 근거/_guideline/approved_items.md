# 에이전트 지침: 승인된 항목

조사 보고서의 항목을 하나씩 설명하고 사용자가 승인한 것만 모은다(#21S-5-1). 지침 초안은 이 목록이 모이면 따로 올린다.
쓰임: 작업 전에 숙지하는 지침, 독립 검사 세션에서 다시 보는 지침, C1~C6 와 lnt review 에 넣고 뺄 후보.

넣는 기준 (#21S-8-13 승인): ln 에만 있는 관례와, 에이전트가 실제로 자주 틀리는 것만 넣는다. LLM 이 이미 아는 일반 원칙은 반복하지 않는다.
지침 초안을 만들 때 이미 승인된 항목도 이 기준으로 한 번 더 거른다.

빠진 항목: 6.2.3(나누는 축, #21S-7-1), 6.2.8(많이 기대받을 모듈은 덜 바뀌게, #21S-8-12), 6.2.11~6.2.14(#21S-9-6).
검사 규칙 단계로 넘긴 것: 6.2.13(결정적 규칙은 훅으로, 판단 신호는 review 질문으로), 6.2.14(함께 자주 바뀌는 모듈 쌍을 review 질문으로).

구조 찾는 순서(#21S-9-1 승인)는 지침이 아니라 세션 시작 훅 출력으로 넣었다(l3.hook_runner, 0.9.0).

## Python 항목

- 1. 지연 표면의 타입 재노출 (#21S-10-3 승인): 도구 수정. lnt doc 이 TYPE_CHECKING 재노출 블록을 쓴다(0.9.0).
- 2. 꺼내 주기 꼴(TypeAlias 대 as 재노출): 꺼내 주기를 새로 쓰지 않기로 해서(#21S-14-2) 필요 없어졌다.
- 3. 공개 이름은 타입만, 함수는 정적 메서드 (#21S-15-3 승인): 규칙 유지. Python 프로토콜 '공개 이름' 절에 까닭을 적었다(0.10.0).
- 넣지 않은 항목 (#21S-16-2 승인): @override 를 typing_extensions 에서 가져오는 문제, TYPE_CHECKING import 를 의존으로 세는 까닭,
  밑줄 없는 안쪽 파일이 타입 검사기에 공개로 보이는 문제, Python 3.15 의 명시적 지연 import.

## Rust 항목

- 1. impl 위치 규칙(C6) (#21S-16-3 승인): 그대로 둔다. RFC 735 가 되돌린 이유(한 번만 쓰는 확장 트레이트)보다 의존이 import 에 드러나는 쪽을 택한다.
- 2. 공개 이름을 타입으로 한정하는 까닭 (#21S-16-4 승인): Rust 프로토콜 '공개 이름' 절에 Python 과 같은 두 줄을 적었다(0.10.0).
- 3. clippy 린트 (#21S-18-3 승인): 새로 켜지 않는다. self_named_module_files 가 잡는 꼴(src/l1.rs 와 src/l1/)은 C7 이 잡고,
  남는 모듈 안 파일 꼴과 인라인 모듈은 D-6. mod_module_files, pub_use, unreachable_pub, redundant_pub_crate 는 생성된 표면과 맞지 않는다.
  lnt init 의 allow-private-module-inception = true 는 유지.
- 4. 경로 규칙(C5)은 Rust 에 두지 않는다 (#21S-22-3 승인). 크레이트는 Cargo 의존으로 꽂아 crate:: 경로가 깨지지 않는다(0.12.0)
- 5. 매크로 (#21S-24-2 승인): 금지하지 않는다. 커뮤니티 합의도 '함수, 제네릭이 먼저, 안 되는 일에만 매크로'다.
  #[macro_export] 는 쓰지 않는다. lnt 가 매크로 정의의 펼칠 코드 안 crate::, $crate:: 경로를 정의한 모듈의 의존으로 센다(0.12.0).
  C8: #[macro_export] 를 위반으로 알린다 (#21S-25-2 승인, 0.12.0). 0.12.0 은 PyPI 까지 올림 (#21S-25-3)
- 마무리 (#21S-18-4 수정, #21S-19-1, #21S-19-2 승인): 남은 14개는 넣지 않는다.
  오류 타입을 모듈마다 둘지 크레이트에 하나만 둘지, 중첩 모듈을 언제 크레이트로 나눌지는 D-6 으로 지침에 두지 않는다.

## 6.2.1 모듈은 처리 단계가 아니라 바뀔 수 있는 결정 하나씩을 맡는다 (#21S-5-3 승인)

- 작업 전: 새 모듈을 만들 때는 그 모듈이 숨기는 결정, 곧 '무엇이 바뀌면 이 모듈만 바뀌는가'를 먼저 정한다. 처리 순서로 나누지 않는다.
- 작업 전 (사용자 덧붙임): 처리 순서대로 나눠야 할 것 같으면 구조를 잘못 이해한 것이다. 숨길 결정을 다시 찾는다. 순서대로 만든 모듈은 앞 단계에 기대게 되어 문제가 생긴다.
- 검사 세션 질문: 결정 하나(형식, 저장 위치, 계산 규칙)가 바뀌면 여러 모듈을 같이 고쳐야 하는가? 그렇다면 그 결정을 한 모듈로 모은다.
- 기계 검사: 어렵다. 결정은 코드에 드러나지 않는다.

## 6.2.2 책임 줄은 '무엇'으로 쓰고, 쓰는 규약을 따른다 (#21S-6-1 승인, 규약은 #21S-8-2 에서 고침)

작업 전 지침 문안(책임 줄 쓰는 법, #21S-8-10 승인판. #21S-8-11 에 따라 대명사 금지 한 줄을 더하는 안을 올림):

```
1. 짧은 한 줄로 쓴다. 모듈 종류에 따라 이렇게 쓴다.
   - 자료형: "~을 나타내는 자료형"
   - 인터페이스: "~을 정의한 인터페이스"
   - 인터페이스 구현: "~의 Python 구현"처럼 무엇을 무엇에 맞게 구현했는지
   - 나머지 모듈: "<입력>을 받아 <출력>을 돌려준다".
     결과가 파일이나 폴더를 바꾸는 일이면 무엇을 바꾸는지 쓴다: "<입력>을 받아 <대상>을 고친다".
2. 동작만 말하고 결과가 없는 동사로 끝내지 않는다. 분석한다, 처리한다, 다룬다, 짚는다, 맡는다, 관리한다, 지원한다, 답한다는 쓰지 않는다.
3. 자연스러운 한국어 기술 용어를 쓴다. 번역투를 쓰지 않는다.
4. 출력을 밝히는 데 꼭 필요한 만큼만 나열하고, 많아야 셋까지 쓴다. 그보다 많으면 대표하는 말로 묶거나 모듈을 나눌지 본다.
5. 어떻게(알고리즘, 함수 이름, 처리 순서)는 쓰지 않는다.
6. 시험: 이 줄만 보고 새 기능이 이 모듈에 들어가는지 판단할 수 있어야 한다.
```

- 프로토콜: "무엇을 맡는지(무엇에 답하는지)" 문구와 예시 줄을 이 규약에 맞춰 바꾼다.
- 검사 세션 질문: 이 줄만 보고 새 기능이 여기 속하는지 판단할 수 있는가?
- 기계 검사: 금지 동사, 접속, 시간어는 글자 검사로 잡을 수 있다. 오탐이 있으니 위반이 아니라 lnt review 질문 후보.
- 후속: 이 프로젝트 지도 전체를 규약대로 고친 안을 올린다(책임 줄은 사람이 정하는 스펙이라 승인 뒤에 고친다).

## 6.2.3 나누는 축은 규칙으로 두지 않는다 (#21S-7-1 승인)

- 무엇을 한 모듈에 두고 무엇을 나눌지는 경우마다 판단이 갈리고, 합당한 판단이면 어느 쪽이든 지적하지 않는다.
- 작업 전 지침, 검사 세션 질문, 기계 검사 어디에도 넣지 않는다.
- 함께 바뀌는 모듈 묶음을 git 이력으로 볼지는 6.2.14 차례에 따로 본다.

## 6.2.4 나누는 데도 비용이 있으니, 지나치게도 모자라게도 나누지 않는다 (#21S-6-3 승인)

- 작업 전: 새 모듈은 숨길 결정이 따로 있을 때만 만든다. 메서드 하나짜리 모듈을 한 모듈만 쓰고 있으면 그 모듈과 합칠지 본다. 한 모듈의 책임 줄에 바뀌는 이유가 둘 보이면 나눈다.
- 검사 세션 질문: 흔한 변경 하나가 몇 개 모듈을 건드리는가? 공개 이름에 비해 하는 일이 적은 모듈이 있는가?
- 기계 검사: 공개 메서드가 하나뿐인 모듈, 기대는 쪽이 한 모듈뿐인 모듈은 계산할 수 있다. 숨길 결정이 따로 있으면 정상이므로 위반이 아니라 lnt review 질문 후보. 크기 상한은 두지 않는다.
- 설명에 쓴 예: order_validator, order_pricer, order_confirmer 로 지나치게 나눈 경우와 order_manager 하나에 몰린 경우. 세 파일 이상을 고치는 과업에서 에이전트 성공률이 10% 아래였다는 조사 결과.
- 지침 초안에서 뺀다 (#21S-26-2 수정: 무엇을 하라는지 없는 문장은 쓰지 않는다). 유일한 구체 조건이던 '메서드 하나짜리 모듈'은 #21S-20-5 의 데이터에서 대부분 정상이었다.
- 지침 문장은 조건과 행동으로만 쓴다. 그렇게 쓸 수 없는 항목은 넣지 않는다 (#21S-26-2).

## 6.2.5 재사용과 분리는 '둘이 같은 이유로 바뀌는가' 하나로 정한다 (#21S-5-2 승인)

작업 전 지침 문안:

```
기능을 더할 때
1. 모듈 지도와 lnt sig 로 그 일을 이미 맡은 모듈이 있는지 아래 층부터 본다. 있으면 그것을 쓴다.
2. 같은 규칙이 두 곳 이상에 있으면 코드 모양이 달라도 한 모듈로 모아 아래 층에 둔다. 이름은 그 규칙이 무엇인지로 짓고 common, utils 같은 이름은 쓰지 않는다.
3. 다른 책임들이 같은 데이터를 쓰면, 데이터와 그 정의는 아래 층 한 모듈에 두고 변환은 각 책임의 모듈에 둔다. 변환 코드가 지금 똑같아도 합치지 않는다.
4. 같은 규칙인지는 "둘이 같은 이유로 바뀌는가"로 정한다.
5. 기능이 그 모듈의 책임 줄에 맞지 않으면 다른 모듈을 찾거나 새 모듈을 만든다. 책임 줄은 고쳐 쓰지 않고 사람에게 올린다.
```

설명에 쓴 예: 모양이 같은 다른 규칙(Username 과 ProductCode 의 is_valid), 모양이 다른 같은 규칙(Invoice 와 Receipt 의 부가세 포함 합계), 공통 원천과 변환(order, invoice, shipping_quote).

## 6.2.6 다른 모듈은 표면에 있는 이름으로만 쓴다 (#21S-7-4 승인)

- 이미 C2 가 강제하므로 새 규칙은 두지 않는다.
- 작업 전 지침(기존 규칙 상기): 다른 모듈이 쓸 일이 없는 클래스와 파일은 이름을 _ 로 시작해 표면에서 뺀다.
- 도구 쪽 할 일(규칙 아님): Python 층·패키지 표면의 이름이 타입 검사기에 Any 로 보이는 문제. Python 항목 차례에 올린다.

## 6.2.7 모듈 사이 순환을 두지 않는다 (#21S-7-5 승인)

- 이미 C4 가 강제하고 해결 순서 네 단계가 C1 메시지에 실리므로 새 규칙은 두지 않는다.

## 6.2.9 의존은 import 로만 드러나게 한다 (#21S-8-5 승인)

- 자기 등록은 이미 프로토콜이 금지한다(Rust 는 inventory, linkme, ctor 도 금지).
- 작업 전: 여러 모듈이 함께 바꾸는 전역 변수를 두지 않는다. 필요한 값은 인자로 넘긴다. 바뀌지 않는 상수와 모듈마다 만드는 로거는 괜찮다.
- 기계 검사: 두지 않는다(공유 여부를 코드만으로 가리기 어렵고 오탐이 많다).

## 6.2.10 판단하는 코드와 바깥과 주고받는 코드를 나누고, 연결은 진입점에서 한다 (#21S-8-6 승인)

- 작업 전: 판단하는 코드는 값을 받아 값을 돌려주게 만들고, 파일, DB, 네트워크, 시계, 난수를 쓰는 코드와 다른 모듈에 둔다. 둘의 연결은 진입점에서 한다.
- 나누는 방법은 값을 주고받는 쪽을 쓴다. 인터페이스(포트)를 두는 방식은 '의존성 역전은 마지막 수단'과 맞지 않는다.
- 기계 검사: 두지 않는다.
- 설명에 쓴 예: Billing.charge_overdue 를 OverduePolicy.overdue(값 → 값)와 진입점의 연결로 나눈 경우.

## 지침 문서: 계획에만 둔다 (#21S-27-1)

지침 문서는 쓸모없이 길다는 판단에 따라 지금은 만들지 않는다. 다시 만들 때 쓸 재료로 #21S-27-1 에 올린 초안의 골자만 남긴다.

- 문장은 조건과 행동으로만 쓴다. 구호 같은 문장은 넣지 않는다 (#21S-26-2)
- 기능을 더할 때: 6.2.5 의 다섯 단계 문안 (예: Invoice 와 Receipt 의 부가세 합계는 한 모듈로, Username 과 ProductCode 의 is_valid 는 합치지 않음)
- 새 모듈을 만들 때: 처리 순서(읽기, 검사, 저장)로 나누지 않고 바뀔 수 있는 결정 하나(파일 형식, 저장 위치, 계산 규칙)를 모듈 하나에 둔다
- 판단과 입출력: 6.2.10 (예: OverduePolicy.overdue(대출 기록, 오늘 날짜) 가 금액을 돌려주고 읽기와 날짜는 진입점이)
- 전역 상태: 6.2.9
- 검사 세션: lnt check 0건, lnt review 질문마다 결정, 결정 하나를 바꿀 때 고칠 모듈 수, 책임 줄로 새 기능 자리를 판단할 수 있는지
- 놓을 곳 안: .claude/for-agent-guideline-ln-structure.md, 세션 시작 훅이 한 줄로 가리킴
